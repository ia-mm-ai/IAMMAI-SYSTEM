# BODY SIGNAL ACCEPTANCE V0 MIN SPEC

## 1. Purpose

This file defines the first bounded body-signal acceptance spec for the
present `IAMMAI-SYSTEM` execution line.

Body-signal recognition now stands. The body-signal recognition v2 line has
also been aligned to live artifact shape, including one live positive
`BODY_PASS_SIGNAL` recognized from a real v0 body-pass artifact and one live
false permission-shaped signal blocked.

The next constitutional distinction is recognition versus acceptance.
Recognition decides whether one candidate indication qualifies as
body-relevant signal. Acceptance decides only whether one `SIGNAL_RECOGNIZED`
result may enter structured handling for one declared bounded matter.

The first lawful matter for this spec is
`current_signal_recognition_standing`, also readable as recognized body-signal
posture. This matter means the current body has standing signal-recognition
posture that may need to be held structurally so recognized signal does not
remain isolated artifact noise and does not inflate into permission.

This file defines acceptance into one declared matter only. It does not define
signal use, signal scope, signal presence, signal threshold, signal truth,
signal routing, an event bus, workflow, action authorization, roadmap
generation, general continuation, governance, or a body relevance medium
implementation.

## 2. Status and Rank

This is an additive v0-min signal-acceptance spec for the present execution
line only.

It ranks below constitutional and reference authority surfaces, including the
preserved `reference/IAMMAI/` surfaces and the current executable source,
tests, artifacts, and standing result surfaces already present in this
repository.

This spec does not create authority. It does not define final governance. It
does not complete continuity. It does not complete final system identity. It
does not replace current executable source, tests, artifacts, self-orientation
results, re-entry results, body-signal boundary, body-signal recognition, or
body-signal recognition v2.

Acceptance through this surface is preparation-side handling only. It is not
scope, presence, threshold, truth, standing state, permission, routing,
workflow, or action.

## 3. Why This Spec Is Needed Now

The body can now recognize one candidate indication as signal. Recognized
signal is not yet accepted signal.

Without acceptance, recognized signal remains an isolated artifact or can be
misread as already entering handling. Without a bounded acceptance surface,
recognized signal may drift into permission, workflow, currentness, routing,
or inflated medium language.

Therefore one bounded body-signal acceptance spec is lawful before any
resolver is built. This is not because signal must be used. It is because a
recognized signal now needs a declared matter if it is to be held
structurally.

## 5. Body-Signal Acceptance Scope

This spec applies only to one `SIGNAL_RECOGNIZED` result and one bounded
signal-acceptance request.

It decides acceptance or blocking for that one recognized signal only. It only
admits recognized signal into a declared matter for structured handling.

It does not:

- scope the accepted signal yet
- establish presence
- establish threshold
- create truth
- create action permission
- route signals
- aggregate signals
- create priority
- create scheduling
- create storage semantics
- create a signal bus
- create an event bus
- create regulation
- create workflow
- create a next-step generator
- authorize action
- authorize follow-on work
- create general continuation
- mutate prior artifacts
- overwrite upstream surfaces
- explain the repository for outsiders

Acceptance is intake into a bounded matter. It is not use, action, routing, or
standing-state formation.

## 6. Required Input Pair

Body-signal acceptance requires exactly two inputs:

1. one `SIGNAL_RECOGNIZED` result
2. one bounded signal-acceptance request declaring the matter for structured
   handling

Both inputs are required.

A blocked signal-recognition result cannot be accepted. A recognized signal
does not automatically become accepted. An acceptance request does not grant
itself acceptance.

The declared matter must be bounded and explicit. For this first spec, the
only supported matter is `current_signal_recognition_standing`.

## 7. Signal-Acceptance Request Shape

The signal-acceptance request is a candidate for acceptance. It is not
permission and does not authorize itself.

### 7.1 `signal_acceptance_request_metadata`

The request must preserve:

- `signal_acceptance_request_id`
- `signal_acceptance_request_type`
- `signal_acceptance_request_version`
- `declared_at`
- `declared_by_surface`

`declared_by_surface` records where the request was made. It does not imply
authority.

### 7.2 `recognized_signal_basis`

The request must preserve:

- `signal_recognition_result_path`
- `signal_recognition_result_id`
- `signal_recognition_result_version`
- `signal_recognition_outcome`
- `signal_recognition_resolver_module`
- `recognized_signal_category`
- `recognized_source_artifact_id`
- `recognized_source_artifact_path`
- `recognized_source_artifact_family`
- `recognized_source_artifact_outcome`

Required posture:

- `signal_recognition_outcome` must be `SIGNAL_RECOGNIZED`
- the recognized signal must remain non-authoritative
- the recognized signal must remain non-permission
- the recognized signal must remain non-currentness

### 7.3 `declared_matter`

The request must preserve:

- `matter_id`
- `matter_family`
- `matter_kind`
- `matter_purpose`
- `matter_boundary`

The first lawful matter is:

- `matter_id = current_signal_recognition_standing`
- `matter_family = body_signal_acceptance_matter`
- `matter_kind = recognized_body_signal_posture`

The matter purpose must remain bounded:

- hold the recognized signal as part of current signal-recognition standing
  posture
- preserve that the signal is recognized but non-operative
- preserve that a false permission-shaped signal was blocked where relevant
- prevent signal from vanishing into artifact noise or inflating into
  permission

The matter must not be:

- action
- route
- workflow
- roadmap
- next step
- general continuation
- system regulation
- body relevance medium implementation

## 8. Acceptance Matter Requirements

The declared matter must be explicit and bounded.

It must name why structured handling is needed. It must preserve that the
recognized signal is being admitted only into a matter, not used, scoped,
routed, acted upon, or made true.

The declared matter must not be:

- action-shaped
- workflow-shaped
- route-shaped
- roadmap-shaped
- a general continuation permission
- a signal-use claim
- a scope claim
- a presence claim
- a threshold claim
- a truth claim

For this first spec, the only supported matter is
`current_signal_recognition_standing`, or exact equivalent wording that
preserves recognized body-signal posture without broadening the matter.

Future matters may require successor specs. This first spec does not open
general matter acceptance.

## 9. Acceptance Checks

A future implementation must perform at least these checks before emitting
`SIGNAL_ACCEPTED`:

- signal-recognition result is readable
- signal-recognition result is well-formed
- signal-recognition result outcome is `SIGNAL_RECOGNIZED`
- recognized signal is present
- recognized signal identity is preserved
- recognized source artifact identity is preserved
- recognized signal category is preserved
- recognized signal remains non-authoritative
- recognized signal remains non-permission
- recognized signal remains non-currentness
- acceptance request is present
- acceptance request is well-formed
- declared matter is explicit
- declared matter is supported
- declared matter is `current_signal_recognition_standing`
- declared matter purpose is bounded to current signal-recognition posture
- acceptance scope preserves that scope is not yet assigned
- acceptance scope preserves that presence is not yet established
- acceptance scope preserves that threshold is not yet met
- acceptance scope preserves that truth is not created
- acceptance does not authorize action
- acceptance does not authorize follow-on work
- acceptance does not route signal
- acceptance does not create workflow, roadmap, event bus, signal router, or
  body relevance medium
- hierarchy constraints are preserved
- correspondence requirements are preserved
- declared non-claims are preserved
- no latest-file recency shortcut is used
- derivative/API/operator/re-entry surfaces do not become governing or current
  basis

Passing these checks means only that the recognized signal may enter the
declared matter for structured handling. It does not mean the accepted signal
has scope, presence, threshold, truth, permission, route, action, or
consequence.

## 10. Refusal / Block Conditions

A future implementation must block acceptance when any of the following holds:

- signal-recognition result unreadable
- signal-recognition result malformed
- signal-recognition result is not `SIGNAL_RECOGNIZED`
- recognized signal missing
- recognized signal identity mismatch
- recognized source identity mismatch
- signal category mismatch
- recognized signal treated as authority
- recognized signal treated as permission
- recognized signal treated as currentness
- acceptance request missing
- acceptance request malformed
- declared matter missing
- declared matter unsupported
- declared matter vague or unbounded
- declared matter attempts action
- declared matter attempts workflow
- declared matter attempts routing
- declared matter attempts roadmap
- declared matter attempts general continuation
- declared matter attempts body relevance medium implementation
- acceptance attempts to create scope
- acceptance attempts to establish presence
- acceptance attempts to meet threshold
- acceptance attempts to create truth
- acceptance attempts to authorize action
- acceptance attempts to authorize follow-on work
- acceptance attempts to create signal router
- acceptance attempts to create event bus
- acceptance attempts to create body relevance medium
- non-claim missing or flipped
- latest-file recency used
- derivative/API/operator/re-entry source collapse

Blocked signal acceptance does not mean the recognized signal is invalid. It
means the request to accept it into structured handling is refused.

## 11. Result Artifact

A future implementation should emit one bounded result artifact with these
top-level sections:

- `body_signal_acceptance_metadata`
- `selected_signal_recognition_result`
- `selected_recognized_signal`
- `selected_signal_acceptance_request`
- `declared_matter`
- `signal_acceptance_checks`
- `outcome`
- `block`
- `accepted_signal`
- `body_signal_acceptance_basis`
- `non_claims`

Minimum metadata:

- `body_signal_acceptance_result_id`
- `body_signal_acceptance_result_type`
- `body_signal_acceptance_result_version`
- `generated_at`
- `resolver_module`

Minimum outcome family:

- `SIGNAL_ACCEPTED`
- `BLOCKED`

For `SIGNAL_ACCEPTED`, `accepted_signal` should preserve:

- accepted signal id and category
- selected signal-recognition result id, path, and outcome
- recognized source artifact id, path, family, and outcome
- declared matter id, family, kind, and purpose
- non-authoritative status
- non-permission status
- non-currentness status
- not-scoped-yet status
- not-present-yet status
- not-threshold-yet status
- not-truth status
- no-action status
- no-routing status
- no-workflow status

For `BLOCKED`, the result should preserve selected recognition result where
available, selected request where available, block code, block reason, failed
checks, and non-claims.

## 12. What Remains Preserved

After signal acceptance or blocking:

- signal-recognition result remains preserved
- recognized signal remains preserved
- acceptance request remains preserved where available
- accepted signal result remains additive
- source remains source
- signal remains signal
- acceptance remains acceptance only
- accepted signal is not scoped yet
- accepted signal is not present yet
- accepted signal has not met threshold
- accepted signal is not truth
- accepted signal does not authorize action
- accepted signal does not authorize follow-on work

Acceptance may hold a recognized signal in a declared matter for structured
handling. It may not use the signal, route the signal, or convert the signal
into permission.
