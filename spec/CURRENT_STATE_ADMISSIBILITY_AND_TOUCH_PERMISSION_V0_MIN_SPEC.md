# Current State Admissibility And Touch-Permission V0-Min Spec

## 1. Purpose

This file defines the first bounded current-state admissibility and touch-permission body-bridge for the v0-min coexistence execution line.

It derives from the visible authority, family, status, governing, transition, re-resolution, successor-adoption, effective-family, current-work-input, current-work-operation, current-state readout, current-state handoff, current-state export, current-state delivery, current-state application, current-state answer/read, current-state query, current-state "what stands now", and current-state "what remains open" stack.

The current-state subsystem now has real bounded readable surfaces. It can answer/read current state, answer one generic current-state query, answer what stands now, and answer what remains open. That makes downstream use possible. The next forced pressure is therefore not more current-state query packaging. The next forced pressure is a narrow admissibility and touch-permission bridge: before broader lawful use, the repo must define when a downstream surface may read, carry, reference, or derive from already-emitted current-state surfaces.

This spec does not rewrite the host, reopen the coexistence proof line, define final governance, define final participation law, complete continuity, invent replay or merge law, define final system identity, create persistence or registry doctrine, or open a broad app, API, chat, dashboard, participation, or workflow framework.

## 2. Status and Rank

This spec ranks below the constitutional and reference authority surfaces in `reference/IAMMAI/`.

This spec is additive. It does not replace the current executable source, tests, or artifacts. It does not modify the authority of the canonical core execution line. It does not define final governance, final currentness doctrine, final system identity law, final participation law, or continuity completion.

This is a bounded current-state body-bridge spec for the present v0-min coexistence execution line only. Its force is implementation-facing: it describes the minimum admissibility and touch-permission posture that a future local resolver would need before using current-state surfaces more widely.

## 3. Why This Spec Is Needed Now

The repo can now resolve and carry current state through answer/read and bounded concrete question families. The current-state subsystem is materially usable.

Without a bounded admissibility and touch-permission bridge, downstream use can become silent touching, implicit authority, hidden mutation, uncontrolled scaling, or accidental promotion of a readable current-state artifact into governing standing. That would collapse distinctions that the current execution line has preserved deliberately.

A narrow bridge is therefore required before this subsystem can be used more widely as part of the larger body. The bridge must say which surfaces may be touched, which touch classes are lawful, what checks must pass, how refusal remains explicit, and what non-claims remain preserved.

## 5. What Admissibility Means Here

Admissibility here is not universal admission into all of IAMMAI.

Admissibility is the bounded determination that a downstream use of the current-state subsystem is lawful to begin. The determination is made against an already-emitted current-state surface, that surface's bounded success outcome, the effective references it depends on where applicable, and the non-claims it carries.

An admissible surface in this slice is a successful current-state result artifact, not a reconstructed live host and not a hidden world-state. Admissibility does not make the selected surface protocol law. It does not upgrade standing, confer sovereignty, create constitutional authorship, or imply full-body participation.

Admissibility may be granted only for a named bounded touch class and a named bounded touch scope. A general desire to use "the current state" is not enough.

## 6. What Touch-Permission Means Here

Touch-permission here is permission to do one or more of the following with an already-emitted current-state surface:

- read it
- carry its bounded identity, path, outcome, summary, or non-claims
- reference it as provenance for another bounded downstream artifact
- derive one bounded downstream result from fields already exposed by the selected surface

Touch-permission is not:

- replay into a live host
- merge of preserved runs or surfaces
- mutation of preserved artifacts
- system identity authority
- constitutional authorship
- hidden promotion from reader to governor
- authority to silently generalize beyond the bounded current-state surfaces
- permission to ignore carried non-claims
- permission to infer latest-emitted standing without an explicit selected surface

The permitted toucher in this slice is only a named local downstream resolver, local inspection surface, or local verification surface acting within this repo line. That label is an engineering description, not a new constitutional role or full participation class.

## 7. Touch Surface Scope

This spec applies only to bounded current-state surfaces that already exist in the current execution line.

Directly admissible touch surfaces are:

- current-state answer/read results with outcome `ANSWERED`
- current-state query results with outcome `ANSWERED_QUERY`
- current-state "what stands now" results with outcome `ANSWERED_WHAT_STANDS_NOW`
- current-state "what remains open" results with outcome `ANSWERED_WHAT_REMAINS_OPEN`

Where a selected surface depends on effective current-state references, touch checks may inspect the named effective authority, family, status, and current-governing artifacts only enough to verify correspondence, canonical line alignment, currentness coherence, and non-claims.

Current-state readout, handoff, export, delivery, and application artifacts remain preserved upstream surfaces. In this bounded slice they are not broad touch targets by default. They may be carried only where the selected admissible surface already exposes them as basis, provenance, or effective-input context.

This spec does not govern the entire repo, every future subsystem, external integration, operator doctrine, vessel doctrine, or a generic participation architecture.

## 8. Touch Classes

The first bounded touch classes are:

- `READ_ONLY_TOUCH`
- `REFERENCE_TOUCH`
- `DERIVATION_TOUCH`

`READ_ONLY_TOUCH` allows inspection of one admitted current-state surface, including its metadata, selected input identity, successful outcome, checks, summary, effective references, and non-claims where exposed. It refuses writes, derivation, replay, merge, mutation, standing upgrade, or use as final governance.

`REFERENCE_TOUCH` allows a downstream bounded artifact to carry or cite one admitted current-state surface by path, id, type, outcome, selected input identity, effective references where exposed, and carried non-claims. It refuses reinterpretation, latest-file inference, stale prior-family fallback, or substitution of a different surface as the active current state.

`DERIVATION_TOUCH` allows one bounded downstream result to be derived from fields already exposed by one admitted current-state surface. It must preserve selected-surface provenance, checks or check summary, admitted touch scope, and carried non-claims. It refuses broad ontology extraction, replay, merge, mutation, final identity claims, continuity completion, standing upgrade, and generic app/API/chat/workflow expansion.

`REFUSED` is an admissibility outcome, not a fourth broad touch class.

## 9. Admissibility Checks

Before any current-state touch is lawful, a future implementation must perform explicit bounded checks.

At minimum, the checks must establish:

- selected current-state surface exists and is readable
- selected current-state surface has a bounded successful outcome supported by this spec
- selected surface is not blocked, malformed, or outside the touch surface scope
- selected surface identity, path, type, and outcome are preserved in the permission result
- effective authority, family, status, and current-governing references remain readable and coherent where the selected surface depends on them
- canonical core execution file remains aligned with `src/integrity_host_v0_min_coexistence_v2.py`
- effective currentness references remain internally coherent
- effective authority, family, status, and governing references name the same current governing source run where those surfaces expose it
- effective authority, family, status, and governing references name the same current governing ingress run where those surfaces expose it
- bounded non-claims remain false, including `replayed_into_live_host`, `merged_into_local_state`, `continuity_completed`, and `standing_upgraded`
- broader carried finality non-claims remain false where exposed by the selected surface
- touch does not silently fall back to stale prior-family artifacts
- touch does not infer active current state from latest authority, family, status, governing, or current-state files alone
- touch request stays within the allowed touch class
- touch request stays within the explicit bounded touch scope
- touch request does not attempt implicit mutation, implicit authority, replay, merge, continuity completion, or standing upgrade

The supported successful source outcomes for this first bridge are:

- `ANSWERED`
- `ANSWERED_QUERY`
- `ANSWERED_WHAT_STANDS_NOW`
- `ANSWERED_WHAT_REMAINS_OPEN`

Any other outcome must be refused unless a later bounded spec explicitly admits it.

Refusal here is a bounded body-bridge refusal. It is not a global constitutional condemnation of the artifact, the repo, a person, an operator, or a future subsystem. It means only that the requested touch is not admissible under this first current-state bridge.

## 11. Future Permission Result Artifact

A future implementation should emit one additive permission result artifact for each admissibility decision.

The smallest bounded artifact shape should preserve:

- `touch_permission_metadata`
- `selected_current_state_surface`
- `touch_request`
- `checks`
- `outcome`
- `block`
- `admitted_touch_scope`
- `non_claims`

`touch_permission_metadata` should preserve:

- `touch_permission_result_id`
- `touch_permission_result_type`
- `touch_permission_result_version`
- `generated_at`
- `resolver_module`

`selected_current_state_surface` should preserve:

- selected surface path
- selected surface id where exposed
- selected surface type where exposed
- selected surface outcome
- selected surface result family, such as answer/read, query, what-stands-now, or what-remains-open
- selected surface effective references where exposed

`touch_request` should preserve:

- touch request id
- requested touch class
- requested touch basis
- requesting local surface or actor label
- intended downstream use in bounded terms
- requested touch fields or references, if the touch is not whole-surface read-only inspection

`checks` should preserve explicit check results or a bounded check summary. Check entries should carry a check name, passed boolean, and expected or actual posture where useful.

`outcome` should use a small bounded result family:

- `ADMITTED_FOR_TOUCH`
- `REFUSED`

`block` should preserve `block_code` and `block_reason` when refused. When admitted, both should be null.

`admitted_touch_scope` should preserve only what has actually been admitted, such as:

- admitted touch class
- admitted source surface path and id
- admitted read fields or references
- admitted carry/reference fields
- admitted derivation boundary if `DERIVATION_TOUCH` was granted
- explicit refusal of replay, merge, mutation, continuity completion, and standing upgrade
