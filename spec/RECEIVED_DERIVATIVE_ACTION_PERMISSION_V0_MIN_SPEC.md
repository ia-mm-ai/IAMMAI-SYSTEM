# Received Derivative Action Permission V0-Min Spec

## 1. Purpose

This file defines the first bounded received-derivative action-permission surface for the v0-min coexistence execution line.

It derives from the current-state subsystem, the current-state admissibility / touch-permission bridge, the continuity-transfer unit, the continuity-transfer receipt surface, and the received-derivative participation surface now standing in this repository line.

The pressure answered here is narrow: after a received derivative has been lawfully participated, what may it actually cause, emit, invoke, or change, in what bounded ways, without silently promoting it into source, authority, local standing, or continuity completion.

This file is about lawful post-participation action permission. It is not another participation package, not a replay path, not a merge path, not a persistence layer, not a registry doctrine, not a final action doctrine, not a final governance framework, not a final continuity doctrine, and not a minimum lawful system declaration.

The next forced pressure is bounded action permission, not a giant abstract agency doctrine.

## 2. Status and Rank

This spec ranks below the constitutional and reference authority surfaces under `reference/IAMMAI/`.

It is additive to the present executable line. It does not replace the canonical executable source, the tests, the emitted artifacts, the current-state surfaces, the touch-permission bridge, the continuity-transfer unit, the continuity-transfer receipt surface, or the received-derivative participation surface.

It does not define final governance, final action law, final participation law, final continuity completion, final system identity law, full operator doctrine, full vessel doctrine, or intelligence participation law.

It is a bounded action-permission spec for the present v0-min coexistence execution line only.

## 3. Why This Spec Is Needed Now

The repository can now resolve current execution authority, preserve run family and status, resolve current governing posture, resolve effective family, consume that effective family, resolve current work, emit current-state surfaces, admit bounded touch, transfer a carried derivative across a seam, receive that carried derivative at a receiving boundary, and participate with the received derivative in bounded ways.

That makes downstream post-participation action materially possible.

Without one bounded action-permission surface, a participated received derivative can still be silently used as if it were source, governing authority, local-state completion, continuity completion, or unrestricted execution standing.

Therefore this spec defines the smallest received-derivative action-permission surface needed before downstream action can scale lawfully.

## 5. What a Participated Received Derivative Means Here

A participated received derivative is a received derivative that has passed a bounded received-derivative participation surface with outcome `PARTICIPATED`.

It is not source. It is not governing authority. It is not final local identity. It is not continuity completion. It is not a replacement for the selected source surface, the transfer unit, the receipt result, the participation result, or the preserved artifact chain that made it readable.

In this bounded slice:

- the selected source surface remains source
- the transfer artifact remains transfer lineage
- the receipt artifact remains receipt lineage
- the participation artifact remains participation lineage
- the participated payload remains derivative / bounded-use lineage
- the participated received derivative may become available only for bounded downstream action

Action permission must not silently collapse source, transfer, receipt, participation, and derivative payload into one undifferentiated local state.

## 6. What Action Permission Means Here

Action permission here means bounded permission for a participated received derivative to emit, invoke, or cause one narrow downstream effect under explicit actor-class, action-class, lineage, payload-scope, and non-claim checks.

It may allow one additive downstream derivative artifact or one bounded downstream surface invocation formed from participated fields and references already preserved by the participation result.

Action permission here is not:

- constitutional authorship
- governing standing
- source identity
- host replay
- preserved-run merge
- mutation of preserved artifacts
- continuity completion
- final action doctrine
- final participation law
- unrestricted execution freedom

Action permission does not grant authority merely because a received derivative was participated. It only says whether one bounded action may proceed from the participated derivative without source replacement, authority promotion, standing upgrade, or continuity-completion claim.

## 7. Action-Permission Source Surface

The action-permission source must be one already-emitted received-derivative participation result with outcome `PARTICIPATED`.

The selected participation result must preserve, where applicable:

- selected participation result identity and path
- selected receipt result identity
- selected transfer result identity
- selected source-surface identity
- selected source-surface family and outcome
- participation payload
- derivative status
- source / transfer / receipt / derivative distinction
- touch-permission lineage where carried
- carried non-claims

Blocked, malformed, unsupported, unreadable, or non-participated participation artifacts do not drive action permission.

Action permission must not infer admissibility from latest current-state, authority, family, status, governing, transfer, receipt, or participation files alone.

## 8. Actor Classes

The first bounded actor classes are:

- `LOCAL_EMISSION_ACTOR`
- `LOCAL_INVOCATION_ACTOR`

`LOCAL_EMISSION_ACTOR` may emit one bounded downstream derivative artifact from already participated fields and references. It may not mutate preserved artifacts, replay the host, merge runs, promote the action payload into source, or claim authority.

`LOCAL_INVOCATION_ACTOR` may invoke one bounded downstream surface with already participated fields and references. It may not promote those fields into source, governing authority, local standing, final identity, or continuity completion.

These are engineering-side bounded action labels for this execution line. They are not constitutional castes, final roles, operator doctrine, vessel doctrine, or intelligence participation law.

## 9. Action Classes

The first bounded action classes are:

- `DERIVATIVE_EMISSION_ACTION`
- `BOUNDED_SURFACE_INVOCATION_ACTION`

`DERIVATIVE_EMISSION_ACTION` permits one additive downstream derivative artifact whose payload is formed only from participated fields and references already exposed by the selected participation result.

`BOUNDED_SURFACE_INVOCATION_ACTION` permits one bounded downstream surface invocation using only participated fields and references already exposed by the selected participation result.

All action classes refuse:

- replay
- merge
- mutation of preserved artifacts
- source replacement
- authority promotion
- continuity completion
- standing upgrade
- final identity claims

No broader action taxonomy is defined here.

## 10. Action Payload Scope

The smallest lawful action-permission payload may include only:

- selected participation result identity and path
- selected receipt result identity and path where preserved
- selected transfer result identity and path where preserved
- selected source-surface identity, family, and outcome where preserved
- bounded participated fields
- bounded participated references
- carried non-claims
- actor class
- action class
- action basis
- explicit derivative status of the action payload

The action payload must not silently include:

- hidden provenance not already exposed
- replay authority
- merge authority
- mutation authority
- constitutional authority
- governing authority
- final identity claims
- continuity completion claims
- source replacement
- latest-file inference

The selected participation result remains the source surface for action permission. The selected source surface remains source. The action-permission payload remains derivative / bounded-action lineage.

## 11. Action Preconditions

Before action permission may begin:

- a successful received-derivative participation result must already exist
- the selected participation result must have outcome `PARTICIPATED`
- the selected participation result must preserve source / derivative distinction
- the selected participation result must preserve selected receipt lineage
- the selected participation result must preserve selected transfer lineage
- the selected participation result must preserve selected source-surface identity
- the selected participation result must preserve touch-permission lineage where applicable
- the selected participation result must preserve carried non-claims
- the action-permission request must name a supported actor class
- the action-permission request must name a supported action class
- the requested action fields must stay within the participated fields and references

Action permission does not bypass participation. It builds on the participation surface rather than replacing it.

## 12. Action Checks

A future resolver must perform at least these checks before emitting an `ACTION_PERMITTED` result:

- selected participation result exists and is readable
- selected participation result has supported successful outcome `PARTICIPATED`
- selected participation result is within action-permission scope
- participation payload is readable and coherent
- participation payload preserves explicit derivative status
- `source_remains_source` remains true
- `receipt_remains_receipt` remains true
- `transfer_remains_transfer` remains true
- `participation_payload_remains_derivative` remains true
- selected source-surface identity remains preserved
- selected transfer result identity remains preserved
- selected receipt result identity remains preserved
- touch-permission lineage remains readable and coherent where applicable
- effective authority, family, status, and governing references remain readable and coherent where the action-permission result depends on them
- canonical core execution file remains aligned with `src/integrity_host_v0_min_coexistence_v2.py`
- effective currentness references remain internally coherent
- bounded non-claims remain false
- action payload scope stays within the participated fields and references
- action does not silently fall back to stale prior-family artifacts
- action does not infer current state from latest files alone
- actor class is one of the bounded supported actor classes
- action class is one of the bounded supported action classes
- action preserves source / transfer / receipt / derivative distinction
- action refuses replay, merge, mutation, continuity completion, standing upgrade, and source replacement

Checks should be explicit enough for a result artifact to show what was permitted or refused without creating a broad schema engine.
