# IAMMAI Relation V0-Min Boundary

## 1. Purpose

This note selects the first relation pressure to derive next from the completed v0-min integrity host proof-slice.

It is derived from:

- `spec/INTEGRITY_HOST_V0_MIN_SPEC.md`
- `spec/INTEGRITY_HOST_V0_MIN_WORLD_ASSUMPTIONS.md`
- `src/integrity_host_v0_min.py`
- `tests/test_integrity_host_v0_min.py`
- the visible reference surfaces under `reference/IAMMAI/`

Its purpose is to answer, at boundary level:

- what relation pressures are now exposed by the runnable host
- which pressure is the most lawful next derivation target
- why that target should be selected before broader relation or system pressures
- what the selected next step would and would not cover

This note is not a constitutional rewrite, full relation doctrine, full system/world-frame definition, minimum lawful system declaration, presence doctrine, runtime architecture rewrite, roadmap, README, manifesto, or project-management note.

## 2. Status and Rank

The v0-min host now stands as a runnable bounded proof. It carries the integrity-kernel proof-slice through code and has a bounded executable test surface around that behavior.

This note ranks below the constitutional protocol, the visible implementation and runtime reference surfaces, the local host spec, the host implementation, the host test surface, and the world-assumptions note. It is additive and does not reinterpret those surfaces.

This note selects a first relation derivation lane. It does not define the full relation layer, full multiplicity law, full coexistence law, full presence doctrine, full system/world-frame, or minimum lawful system.

## 3. Why This Note Is Needed Now

The current host is complete enough at its rank. It no longer exists only as theory; it is a bounded mechanism with explicit phase movement, standing-only resolution, orthogonal HOLD, append-only records, explicit refusal, and predecessor relation on `EVOLVE`.

Because the host now runs, the one-host and one-open-object assumptions are no longer abstract simplifications. They are visible operating boundaries.

More than one next pressure is now visible:

- same-host multiplicity and coexistence
- relation between multiple objects tied to one or overlapping matters
- host-to-host continuity
- persistence and registry relation beyond local memory
- context or world-boundary modeling beyond one local host

The body therefore needs one small boundary note to choose the lawful next derivation lane instead of widening in many directions at once.

## 4. What Now Stands

The current line now materially has:

- a runnable host proof-slice
- a bounded in-memory kernel-host mechanism
- a test surface that locks the hostability behavior
- a world-assumptions note exposing the assumptions hidden inside the host
- a clear distinction between what the host proves, what the host assumes, and what remains open beyond it

This proves hostability of the bounded kernel slice. It does not prove full relation law, full embodiment, distributed continuity, final persistence architecture, final presence doctrine, or minimum lawful system.

## 5. Relation Pressures Exposed By The Current Host

The current host exposes relation pressure by holding relation outside the proof boundary except for one explicit predecessor relation on `EVOLVE`.

The main exposed pressures are:

- same-host multiplicity / coexistence: the host currently permits only one unresolved open object at a time, which avoids relation among concurrent objects rather than solving it
- multiple objects tied to one matter: the host can preserve a successor object, but it does not define how several objects on the same matter may coexist outside the single predecessor/successor case
- overlapping matters: the host assumes `matter_ref` is already bounded enough for local handling, but it does not define how adjacent or overlapping matters relate
- host-to-host continuity: the host assumes one local execution boundary and does not define what preserves continuity across hosts or carriers
- persistence / registry relation: the host uses in-memory append-only records and does not define how those records relate to a final registry or durable preservation layer
- context / world-boundary relation: the host assumes the relevant context is already supplied by local references and does not model the wider boundary in which those references count
- relation between standing matters: once multiplicity exists, standing objects may need explicit relation handling so standing does not become isolated fragments or silent contradiction

These are candidate pressures. They are not doctrines.

## 6. Candidate Next Derivation Lanes

### 6.1 Same-Host Multiplicity / Coexistence

This lane is visible because the host currently refuses a second unresolved open object. That refusal is lawful for the proof-slice, but it exposes the next relation question: what happens when more than one object must exist inside one host boundary?

This is the best immediate next lane because it remains adjacent to the current runnable host. It can be derived by relaxing or specifying the host-local one-open-object simplification without jumping into distributed coordination, final persistence architecture, or full world ontology.

It still presupposes work the current host has not done: a bounded distinction between independent coexistence, related coexistence, contradiction, successor relation, and unresolved open relation inside one host.

### 6.2 Cross-Host Continuity

This lane is visible because the current host assumes one local host and one local state boundary.

It is not the best immediate next lane. Cross-host continuity needs answers about object relation, record relation, authority boundary, and persistence that the same-host slice has not yet made explicit. Starting here would risk turning host-boundary pressure into premature system closure.

It presupposes at least a minimal account of how multiple objects relate before asking how multiple hosts carry or preserve those relations.

### 6.3 Persistence / Registry Relation

This lane is visible because the host uses append-only in-memory records, while the reference body treats registry/store preservation as a distinct runtime concern.

It is not the best immediate next lane. Persistence architecture should preserve relation; it should not invent relation by storage design. A registry derivation before a coexistence boundary would risk encoding an underspecified relation model as infrastructure.

It presupposes a clearer account of what relations among objects and records must be preserved.

### 6.4 Broader Context / World-Boundary Modeling

This lane is visible because the host assumes `matter_ref`, `payload_ref`, `occurrence_ref`, and `basis_ref` are already meaningful enough for bounded local execution.

It is not the best immediate next lane. Context and world-boundary modeling are broader than the current proof pressure requires. Moving there now would risk turning open relation questions into inflated system theory.

It presupposes answers about multiplicity, coexistence, matter relation, presence relation, and standing relation that the current proof line has not yet derived.

## 7. Selected First Relation Target

The selected first relation slice is:

**bounded same-host multiplicity / coexistence boundary**

This is the lawful next target because:

- it is the nearest pressure exposed by the one-open-object simplification
- it remains adjacent to the current runnable host
- it lets relation emerge from the existing proof instead of jumping to distributed or system-wide questions
- it is smaller and more falsifiable than cross-host continuity, final persistence architecture, or context/world-boundary modeling
- it begins relation work without pretending to complete the whole system
- it begins 6 without falsely claiming 9

This selection does not reopen the completed host slice. The v0-min host remains valid at its own rank. The next relation step would examine what must be added or bounded when the one-open-object simplification is no longer sufficient.

## 8. What The Selected Next Step Would Cover

A bounded same-host multiplicity / coexistence derivation would need to decide, in first-pass form:

- whether more than one object may coexist inside one local host
- whether more than one unresolved open object may ever exist inside one local host
- whether multiple candidate objects may coexist
- whether multiple present objects may coexist
- whether multiple unresolved standing objects may coexist
- whether resolved standing objects coexist differently from unresolved standing objects
- what kinds of object relation must be explicit when objects share a matter or overlap matters
- whether the existing predecessor relation is enough only for `EVOLVE`, or whether other coexistence relations require their own explicit markers
- what contradictions or conflicts must be refused rather than hidden behind ordering, naming, or storage convention
- how append-only records must preserve coexistence decisions and refusals
- how HOLD behaves when more than one object exists inside the same host boundary

This would be a boundary-level relation derivation. It would not be a full relation spec until those choices are stated precisely enough for later implementation or tests.

## 9. What The Selected Next Step Would Not Cover

The selected next relation slice would not yet settle:

- full many-kernel coexistence law

It would remain inside one host boundary and would ask only what lawful coexistence requires there.

## 10. Presence Boundary

Presence remains relevant to relation work because coexistence and occurrence are not unrelated.

The current host requires explicit `occurrence_ref` handling before an object becomes `PRESENT`, and standing remains impossible without presentation. If multiple objects later coexist, their occurrences may need to remain distinguishable so presence does not collapse into generic basis language or hidden context.

This note does not select presence doctrine as the next standalone derivation target. Presence may reappear as a constraint inside the same-host coexistence boundary, but it must not replace the selected relation lane or dominate it beyond what the current host actually forces.

This note does not settle all occurrence forms, witness requirements, event boundaries, or cross-layer presence continuity.
