# Portable Source-Body Verification Boundary V0 Minimum Specification

## 1. Purpose

This file defines the portable source-body verification boundary for the present `IAMMAI-SYSTEM` execution line.

This is the next lawful carrier-independence membrane after `SOURCE_BODY_RECEPTION_BOUNDARY_CHAIN_TERMINAL_SUMMARY_V0.md`.

The purpose of this boundary is to define whether one selected closed source-body basis can be verified away from the original technical carrier without trusting the original device, local filesystem path, operating system, vendor environment, hidden local state, latest-file posture, repository possession, artifact existence alone, carrier possession alone, or human narration.

This file does not implement verification.

This file does not create runtime portability, source-body transfer, source-body migration, carrier expansion, multi-carrier standing, deployment, publication, public release, product packaging, operation permission, final completion, reusable permission, continuation, or follow-on work.

Portable verification is not portability-as-runtime.

Portable verification is not deployment.

Portable verification is not public release.

Portable verification is not source transfer.

Portable verification is not source receipt.

Portable verification is not carrier expansion.

Portable verification is not multi-carrier standing.

Portable verification is not another reception request.

Portable verification is only a boundary for verifying that a selected closed source-body basis can be checked on another technical carrier without the carrier becoming source, authority, currentness, adoption, operation permission, publication flow, public readiness, final completion, continuation, reusable reception permission, or follow-on authority.

## 3. Why This Spec Is Needed Now

The source-body reception chain has closed as a bounded anti-capture reception-family review line.

Source-body reception closure did not authorize source receipt, reception authorization, adoption, authority, currentness, operation permission, public readiness, final completion, continuation, reusable permission, successor reception, or follow-on work.

The source-body reception terminal summary records that the closed reception line sealed itself without capture and without becoming permission.

After closure, the next structural risk is carrier-dependence.

If the body can only be verified on one laptop, one operating system, one folder, one account, one repository, one cloud, or through one human narrator, then later complexity inherits hidden carrier dependence.

Portable verification is the carrier-independence membrane before derivative participants, vessel relation, runtime hosting, deployment, public release, product integration, or carrier packet work can be considered by any separately specified boundary.

The question is whether the source-body can be verified as itself on another technical carrier without carrier capture.

This boundary exists to prevent verification from being overread as transfer, migration, source receipt, carrier authority, path currentness, repository currentness, public readiness, operation permission, final completion, reusable permission, or continuation.

## 4. Definitions

`portable_source_body_verification` means checking one selected closed source-body basis from declared evidence on a technical carrier while preserving that verification is not transfer, migration, source receipt, reception authorization, adoption, authority, currentness, runtime hosting, deployment, public release, operation permission, final completion, reusable permission, continuation, or follow-on work.

`selected_closed_source_body_basis` means the selected source-body surfaces, closure records, tests, artifacts, terminal summaries, and bounded evidence that define what is being verified.

`selected_reception_closure_basis` means the selected source-body reception closure record and associated basis used as evidence that the reception-family boundary chain closed without authorizing permission.

`selected_terminal_summary_basis` means the source-body reception terminal summary or other terminal summary surface selected as readability evidence for the closed line.

`verifying_carrier` means the technical carrier or context attempting to verify the selected closed source-body basis.

`original_carrier` means the technical carrier or context from which the selected basis was first handled, stored, generated, or observed.

`technical_carrier` means a device, operating system context, filesystem, repository clone, account, cloud environment, archive, mirror, or interface capable of holding declared evidence.

`carrier_independent_verification` means verification that does not depend on the original carrier, a local path, latest-file posture, recency, hidden local state, vendor environment, operating system identity, repository possession, artifact existence alone, carrier possession alone, or human narration.

`verification_evidence` means declared source surfaces, spec surfaces, resolver surfaces, test surfaces, artifact roots, closure records, terminal summaries, manifests, checksums, signatures, or other bounded evidence if separately specified.

`required_body_surfaces` means the selected source, spec, resolver, test, artifact, closure, and terminal-summary surfaces required to check the selected closed source-body basis.

`required_closure_records` means selected closure artifacts or terminal summaries that record closed boundary state without authorizing permission.

`required_artifact_roots` means declared artifact directories that may be inspected as evidence without making artifact existence currentness.

`required_test_surfaces` means declared tests or test surfaces that may be used as verification evidence without creating runtime hosting, deployment, operation permission, or final completion.

`manifest_candidate` means future evidence language for a possible manifest surface. It is not a manifest implementation in this spec.

`checksum_candidate` means future evidence language for a possible checksum or signature surface. It is not a checksum implementation in this spec.

`hidden_local_state` means any undeclared state on a carrier, filesystem, shell, application, cache, account, registry, cloud, environment variable, or interface that would be needed to verify the body.

`device_authority` means an invalid posture in which a device is treated as source, authority, or currentness source.

`os_authority` means an invalid posture in which an operating system identity is treated as source, authority, or currentness source.

`vendor_authority` means an invalid posture in which a vendor environment, account, cloud, app, model, host, or tool is treated as source, authority, or currentness source.

`path_currentness` means an invalid posture in which a local filesystem path creates currentness.

`recency_currentness` means an invalid posture in which latest-file posture, timestamp, recent generation, or recent possession creates currentness.

`repository_possession_currentness` means an invalid posture in which repository clone possession creates body standing or currentness.

`narrator_trust_currentness` means an invalid posture in which human narration creates source identity, authority, or currentness.

`carrier_capture` means verification collapses into carrier possession, device authority, operating system authority, vendor authority, repository possession, path currentness, artifact existence, or narration.

`source_replacement_by_carrier` means an invalid posture in which a carrier, repository copy, archive, mirror, path, account, or environment becomes a replacement for source.

`verification_only_posture` means the verifying carrier may hold and check declared evidence without becoming source, authority, currentness selector, adoption surface, operation surface, public release, runtime host, or permission-bearing environment.

Portable verification means checking a selected closed source-body basis from declared evidence on a carrier.

The verifying carrier does not become source.

The original carrier does not remain authority merely because it was original.

Path, recency, latest file, repository possession, artifact existence, carrier possession, archive possession, or narration cannot create currentness.

Manifest and checksum language in this spec is future evidence language only, not implementation.

## 21. Closing Boundary Statement

Portable source-body verification boundary may record that one selected closed source-body basis can be verified from declared evidence on a technical carrier without the carrier, device, operating system, vendor, account, path, recency, latest file, repository copy, artifact existence, or narration becoming source, authority, or currentness. It preserves that verification is not transfer, migration, source receipt, reception authorization, adoption, operation permission, public readiness, final completion, continuation, reusable permission, derivative reception, vessel relation, public release, deployment, runtime hosting, or follow-on work.

It closes the question:

`Can this selected closed source-body basis be verified on another technical carrier without carrier capture or carrier authority?`

It does not open the question:

`Can the body be transferred, migrated, deployed, hosted, published, operationalized, adopted, currentized, or continued now?`
