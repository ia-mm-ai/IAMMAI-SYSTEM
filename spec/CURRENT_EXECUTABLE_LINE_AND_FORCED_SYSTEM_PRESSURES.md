This file is a bounded clarification note for the current `IAMMAI-SYSTEM` executable stack.

It exists because the repository now has a large enough executable and inspection body that current execution authority and next pressure need to be stated plainly. The repo now contains a runnable host line, scenario emission, import, review, comparison, receiving packet, validation, ingress decision, run-level ingress, and source-to-ingress comparison surfaces. ## 9. Forced System Pressures Now Visible

The working line now forces the following first system pressures into visibility.

### 9.1 Canonical Execution Authority Pressure

One line must now be treated as current execution authority. The current answer is `src/integrity_host_v0_min_coexistence_v2.py` as canonical core, with the surrounding snapshot, scenario, import, review, receiving, ingress, and comparison files as derivative support.

Without that distinction, predecessor proof hosts and derivative utility surfaces can appear as competing current lines.

### 9.2 Multi-Run / System Identity Pressure

The repo now emits source runs, review artifacts, receiving packets, ingress decisions, ingress runs, and comparisons. Once many such runs exist, a question becomes unavoidable: what constitutes system-level identity beyond one source run or one host slice?

The current answer is only bounded path correspondence and preservation comparison. It is not yet system identity law.

### 9.3 Receiving-Lane Multiplicity Pressure

A single receiving packet can be built, validated, and decided. A run-level ingress lane can process multiple scenario artifacts. Once multiple decisions exist together, their relation becomes visible.

The current line preserves each decision and aggregates counts. It does not yet define a stronger receiving-side system relation among decisions.

### 9.4 Currentness / Recency Pressure

The runners commonly select lexically latest `run_*` directories or latest matching artifacts. That is a local engineering convention for bounded scripts.

It is not currentness doctrine. A later lawful system must distinguish "latest emitted" from "current governing" before any stronger authority is inferred from recency.

### 9.5 Bounded Continuity Pressure

The receiving lane keeps source, import, receiving packet, validation result, decision, and ingress run distinct. That separation now forces the boundary question: what would have to be added before preservation and bounded receiving can become any stronger continuity claim?

The current answer is explicit non-completion: `continuity_completed = false`, no replay, no merge, no standing upgrade.

### 9.6 Local-Host-To-System Pressure

The host line remains local and bounded, but its support surfaces now behave like a small system around it. Some assumptions remain clearly host-local: in-memory host state, local object ids, local relation markers, local artifact roots, and latest-run selection.

Other assumptions are starting to behave like unavoidable system assumptions: canonical execution authority, source/import/receiving distinction, refusal visibility, append-only trace visibility, relation count preservation, HOLD visibility, lineage visibility, and explicit non-claims around replay, merge, standing upgrade, and continuity completion.

The pressure is to separate those two classes before building more machinery.
