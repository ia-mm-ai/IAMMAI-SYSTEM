## 4. Definitions

`admitted_request` means the v2 one-shot single live command invocation request that was admitted as request/admission posture only. It is not request consumption, command invocation, command execution, command output, command result, command success, standing lane, repeat permission, authority, currentness, final completion, continuation, reusable permission, or follow-on work.

`v2_admitted_request_basis` means selected v2 admission evidence, by reference-shaped basis only, that preserves outcome `SINGLE_LIVE_COMMAND_INVOCATION_REQUEST_ADMITTED`, result version `0.2.0`, failed check count zero, v2 successor metadata, v1 predecessor relation, returned-result containment posture, and no invocation/execution/output/result/success posture. The selected clean v2 artifact may be referenced only if it preserves those fields; artifact path or existence alone is not authority or currentness.

`request_consumption_boundary` means this bounded specification line defining whether and how an admitted v2 request may later be consumed once by a separately bounded execution review. It does not consume the request here.

`consumption_review` means a future bounded review that may inspect the admitted v2 request basis and this boundary before any later execution review. This specification does not create that review.

`request_consumed` means a later separately recorded event or posture in which the admitted request is used as consumed basis. This specification does not create that event or posture.

`one_shot_consumption` means consumption, if later separately authorized, is limited to one admitted request and one future consumption relation only. It creates no standing lane and no repeat permission.

`standing_invocation_lane` means any general or durable posture that would allow ongoing command invocation without a separately bounded review each time. This boundary creates no such lane.

`repeat_invocation_permission` means any permission to invoke the command more than once, invoke by reuse, or treat one admitted request as a reusable run authorization. This boundary creates no repeat permission.

`command_invocation` means the act of causing the command module, function, script, shell, CLI, workflow, or comparable execution surface to run. This boundary does not create command invocation.

`command_execution` means the actual execution event or live run of the command. This boundary does not perform command execution.

`command_output` means output emitted by a separately authorized live command invocation. This boundary creates no command output.

`command_result` means a result object produced by a separately authorized live command invocation. This boundary creates no command result.

`command_success` means successful command execution, successful return, exit status, passed check set, or comparable success posture from a later live run. This boundary creates no command success.

`execution_permission_overread` means treating request admission, request consumption boundary, artifact existence, path, latest-file posture, passed checks, repository copy, carrier possession, environment, timestamp, or narration as permission to run the command. This boundary prohibits that overread.

`admission_as_execution_collapse` means treating admitted request posture as if command invocation or execution has occurred. This boundary blocks that collapse.

`request_admission_currentness_overread` means treating v2 request admission as creating currentness for source, command, artifact, repository, carrier, output, result, success, path, or next work. This boundary blocks that overread.

`v1_predecessor_failure_evidence` means the visible v1 predecessor line and containment flaw evidence. It must remain visible. It is not erased, repaired, hidden, or converted into a clean admission basis by v2 or this boundary.

`v2_successor_containment` means the successor behavior that detects forbidden full-prior-artifact-body posture and prevents raw full prior artifact body content from returning in result content. This boundary must preserve that posture.

`separate_execution_review` means a future, separately specified boundary or review required before any command invocation or execution may occur. This specification does not create it.

Request consumption boundary means defining whether and how an admitted request may later be consumed once, not consuming it here.

One-shot consumption means no standing lane and no repeat permission.

The v2 admitted request basis must not erase v1 predecessor failure evidence.

Command execution remains separately bounded future work.
