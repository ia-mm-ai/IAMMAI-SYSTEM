# CURRENT SELF-ORIENTATION RE-ENTRY ADMISSIBILITY V0 MIN SPEC

## 1. Purpose

This file defines the first bounded current-self-orientation re-entry
admissibility spec for the present `IAMMAI-SYSTEM` execution line.

Current self-orientation re-entry admissibility is a bounded gate that decides
whether one declared next relation, touch, or work step may lawfully proceed
from one `SELF_ORIENTED` result without that self-orientation result becoming
authority.

Self-orientation lets the body find itself from preserved artifacts. Re-entry
admissibility asks whether one declared next bounded step may enter through
that recognized posture.

The gate asks only:

`May this specific SELF_ORIENTED result be admitted as the bounded re-entry
basis for this one declared next step?`

This file exists because current self-orientation v2 now stands as a bounded
internal recognition surface. The next pressure is not another organ
immediately. The next pressure is whether one declared next step may lawfully
enter through that recognized posture while preserving source, derivative,
operator, open, blocked, and non-claim distinctions.

This file defines the smallest lawful gate between recognition and
continuation. It does not define implementation code, tests, schemas, generated
views, workflows, orchestration, roadmap generation, final governance,
continuity completion, or final system identity.

## 2. Status and Rank

This is an additive v0-min re-entry admissibility spec for the present
execution line only.

It ranks below constitutional and reference authority surfaces, including the
preserved `reference/IAMMAI/` surfaces and the current executable source,
tests, and artifacts that already stand in the repository.

This spec does not create authority. It does not define final governance. It
does not complete continuity. It does not complete final system identity. It
does not replace current executable source, tests, standing artifacts, or
current self-orientation results.

This spec defines a bounded admission/refusal surface. Admission through this
surface is not authority creation, not source creation, not a standing upgrade,
and not permission for follow-on work.

## 3. Why This Spec Is Needed Now

The body can now find itself from preserved artifacts through current
self-orientation. That creates a new pressure: whether one next step may
lawfully proceed from that recognized posture.

Without a bounded re-entry admissibility surface, self-orientation risks
drifting into fake sovereignty, general permission, or a convenience feedstock
for future work. That would collapse recognition into authority.

The next lawful question is therefore not `what else can the body summarize?`
The next lawful question is:

`May this one declared step enter through that found-self while preserving
hierarchy?`

One bounded re-entry admissibility spec is required before any resolver is
built.

## 4. What Now Stands

The following surfaces now materially stand as relevant context for this gate:

- current self-orientation v2 as an internal derived recognition surface
- current-state answer/read, query, what-stands-now, what-remains-open, and
  admissibility/touch-permission surfaces
- continuity transfer unit and continuity transfer receipt surfaces
- received derivative participation and received derivative action-permission
  surfaces
- continuity memory seam surface
- v0 body-pass surface
- bounded OpenAI API derivative vessel v3 surface
- operator-facing terminal brief surface
- carried non-claims that remain false

This is not a whole-body recap. These surfaces are named only because a
re-entry request must not shift or blur the basis that self-orientation already
recognized.

## 5. Re-Entry Admissibility Scope

This surface applies only to one `SELF_ORIENTED` result and one declared next
bounded request.

It decides admission or refusal for one next declared step only.

It does not:

- decide the body's roadmap
- generate the next task
- authorize follow-on work
- mutate prior artifacts
- overwrite upstream surfaces
- define body-wide workflow
- define signaling or regulation
- define replay or merge law
- explain the repository for outsiders
- turn self-orientation into a general permission object
- turn self-orientation into source, governing, current, derivative, or
  operator authority

Re-entry is not generic self-orientation consumption. It is not general
downstream feedstock. It is one gate between recognition and continuation.

## 6. Required Input Pair

The gate requires exactly two inputs:

1. one `SELF_ORIENTED` result
2. one bounded re-entry request

Both inputs are required.

A blocked, refused, unreadable, or malformed self-orientation result cannot
serve as admissible basis.

A vague or unbounded request cannot be evaluated lawfully.

If the request cannot answer what exact step is requested, through which
self-orientation result, from which locked recognized basis, against which
target surface, for what purpose, and under what limits, the request is too
vague and must block.

## 7. Re-Entry Request Shape

The re-entry request is a candidate for admission. It is not a permission slip.
It must be boring, explicit, and bounded.

### 7.1 `reentry_request_metadata`

The request must preserve:

- `reentry_request_id`
- `reentry_request_type`
- `reentry_request_version`
- `declared_at`
- `declared_by_surface`

`declared_by_surface` records where the request was declared. It does not
imply authority.

### 7.2 `self_orientation_basis`

The request must preserve:

- `self_orientation_result_path`
- `self_orientation_result_id`
- `self_orientation_result_version`
- `self_orientation_outcome`
- `self_orientation_resolver_module`

Required posture:

- `self_orientation_outcome` must be `SELF_ORIENTED`
- the result should preferably come from the current standing
  self-orientation successor line
- the self-orientation result may be cited as recognition basis only, not as
  source authority

### 7.3 `locked_orientation_basis`

This section is required.

The request must explicitly lock the upstream basis it is asking to proceed
from. It must not merely cite a valid self-orientation artifact while quietly
shifting basis.

At minimum it must preserve:

- `selected_body_pass_result_id`
- `selected_body_pass_result_path`
- `selected_source_surface_id`
- `selected_source_surface_path`
- `selected_current_state_answer_read_id`
- `selected_current_state_answer_read_path`
- `selected_what_stands_now_id`
- `selected_what_stands_now_path`
- selected effective references, including:
  - `effective_authority_artifact_path`
  - `effective_family_packet_path`
  - `effective_status_packet_path`
  - `effective_current_governing_packet_path`
  - `effective_source_run_path`
  - `effective_ingress_run_path`

The purpose of this lock is not to create new authority. The purpose is to
prevent a request from piggybacking on a valid self-orientation result while
substituting a different current, governing, source, or current-state basis.

### 7.4 `declared_next_step`

This is the heart of the request.

The request must preserve:

- `next_step_family`
- `next_step_kind`
- `target_surface_family`
- `target_surface_path`
- `target_surface_id`
- `declared_purpose`
- `declared_expected_output_family`
- `requested_relation_to_basis`

`next_step_family` must be one of this small family:

- `SPEC_BOUNDARY`
- `RESOLVER_IMPLEMENTATION`
- `TEST_SURFACE`
- `ARTIFACT_EXECUTION`
- `DERIVATIVE_READ`
- `OPERATOR_FACING_DERIVATIVE`
- `CONTINUITY_TOUCH`

The request must not say `continue the work`, `advance IAMMAI`, `determine the
next organ`, or `self-generate the next lawful step`.

`requested_relation_to_basis` must state how the requested step relates to the
recognized posture. Acceptable examples include:

- spec successor from self-orientation
- test successor for re-entry gate
- derivative read from recognized current-state
- bounded continuation from recognized open surface

### 7.5 `declared_scope_bounds`

The request must preserve:

- `one_step_only`
- `additive_output_only`
- `allowed_new_file_paths`
- `allowed_artifact_output_roots`
- `allowed_read_surfaces`
- `forbidden_read_surfaces`
- `forbidden_write_surfaces`

Required posture:

- `one_step_only = true`
- `additive_output_only = true`
- no upstream mutation
- no overwrite
- no hidden broad repository scan unless explicitly necessary and bounded
- writes, when admitted, must stay inside the declared additive output paths
  or artifact roots

### 7.6 `hierarchy_constraints`

The request must preserve:

- `current_governing_basis_source`
- `derivative_surfaces_allowed_as_basis`
- `operator_surfaces_allowed_as_basis`
- `self_orientation_allowed_as_authority`
- `currentness_may_be_inferred_by_recency`

Required posture:

- `derivative_surfaces_allowed_as_basis = false`
- `operator_surfaces_allowed_as_basis = false`
- `self_orientation_allowed_as_authority = false`
- `currentness_may_be_inferred_by_recency = false`

Current and governing basis must remain upstream-derived from explicit
current, effective, governing, and current-state surfaces. Derivative API and
operator-facing surfaces may be recognized as downstream posture only.

### 7.7 `correspondence_requirements`

The request must carry proportion pressure forward by preserving:

- `must_preserve_current_basis`
- `must_preserve_open_surfaces`
- `must_preserve_blocked_refused_surfaces`
- `must_preserve_derivative_source_distinction`
- `must_preserve_non_claims`
- `must_prevent_over_mirroring`
- `must_prevent_under_mirroring`

These requirements prevent the next step from turning recognition into a
whole-body replacement, or from thinning recognized posture into a vague
summary.

### 7.8 `requested_permissions`

This section must remain narrow.

The request must preserve:

- `read_permission_requested`
- `derive_permission_requested`
- `emit_permission_requested`
- `mutate_permission_requested`
- `replay_permission_requested`
- `merge_permission_requested`
- `authorization_scope`

Required posture for ordinary lawful re-entry:

- read may be true
- derive may be true
- emit may be true only for one new additive artifact or file
- mutate must be false
- replay must be false
- merge must be false
- `authorization_scope = "single_declared_step_only"`

### 7.9 `declared_non_claims`

The request must preserve:

- `does_not_create_authority = true`
- `does_not_complete_continuity = true`
- `does_not_complete_final_governance = true`
- `does_not_complete_final_system_identity = true`
- `does_not_upgrade_standing = true`
- `does_not_replace_source_surfaces = true`
- `does_not_upgrade_derivative_outputs_to_source = true`
- `does_not_create_general_permission = true`
- `does_not_authorize_follow_on_steps = true`

Missing or flipped non-claims must block.

### 7.10 `refusal_acknowledgement`

The request must preserve:

- `request_may_be_blocked`
- `blocked_result_must_preserve_basis`
- `no_fallback_to_human_narration`
- `no_fallback_to_latest_file`

Required posture:

- `request_may_be_blocked = true`
- `blocked_result_must_preserve_basis = true`
- `no_fallback_to_human_narration = true`
- `no_fallback_to_latest_file = true`

## 8. What a Request Must Not Contain

A lawful re-entry request must not contain:

- a whole Codex prompt
- generated file contents
- a doctrine recap
- a roadmap
- vague phrases such as `continue the work`, `advance IAMMAI`, or `determine
  the next organ`
- broad permission such as `use current orientation for future work`
- autonomous self-generation language
- hidden workflow machinery
- hidden body-wide signaling or regulation claims
- derivative, API, or operator-facing authority upgrades
- recency-based basis substitution

The request should declare one bounded candidate step. It should not decide
what the body wants or what the system should become.

## 9. Re-Entry Admissibility Checks

A future implementation must perform at least these checks before emitting
`REENTRY_ADMITTED`:

- the selected self-orientation result is readable
- the selected self-orientation result is well-formed
- the selected self-orientation result has outcome `SELF_ORIENTED`
- the locked orientation basis matches the self-orientation result
- the locked upstream basis remains readable
- current and governing basis still comes from upstream current, effective,
  governing, and current-state surfaces
- derivative, API, and operator-facing surfaces remain downstream only
- open surfaces remain open
- blocked and refused surfaces remain visible
- non-claims remain false
- no latest-file recency shortcut is used
- self-orientation is not treated as source authority
- the requested next step is explicit and bounded
- the request does not exceed what the recognized posture supports
- admission would not become roadmap, autonomy, or signaling by stealth
- admission would not authorize follow-on steps
- requested mutation, replay, merge, overwrite, or broad scan is absent
- requested output is additive and limited to the declared single step

`REENTRY_ADMITTED` may be emitted only when these checks remain proportioned to
the recognized self-orientation result and the declared next step.

## 10. Refusal / Block Conditions

The re-entry admissibility result must block explicitly for at least these
conditions:

- self-orientation result is not `SELF_ORIENTED`
- self-orientation result is unreadable
- self-orientation result is malformed
- locked orientation basis is missing
- locked orientation basis mismatches the self-orientation result
- locked upstream basis is no longer readable
- current or governing basis is inferred from derivative, API, or
  operator-facing surfaces
- request is vague or unbounded
- request exceeds recognized posture
- open surfaces are treated as completed
- blocked or refused surfaces are hidden
- non-claims are missing or flipped
- self-orientation is treated as source authority
- admission becomes roadmap, autonomy, or signaling by stealth
- request attempts mutation, replay, or merge
- request attempts overwrite or source replacement
- request attempts follow-on authorization
- request attempts general future-work permission
- request falls back to latest-file recency
- request falls back to human narration instead of bounded evidence

Blocked re-entry is not blocked current-state and not blocked
self-orientation. It is refusal of continuation through that selected basis.

## 11. Result Artifact

A future implementation must emit one bounded result artifact with at least
these top-level sections:

- `current_self_orientation_reentry_admissibility_metadata`
- `selected_self_orientation_result`
- `locked_orientation_basis`
- `selected_reentry_request`
- `reentry_admissibility_checks`
- `outcome`
- `block`
- `reentry_admissibility_basis`
- `non_claims`

Minimum metadata:

- `reentry_admissibility_result_id`
- `reentry_admissibility_result_type`
- `reentry_admissibility_result_version`
- `generated_at`
- `resolver_module`

Minimum outcome family:

- `REENTRY_ADMITTED`
- `BLOCKED`

`selected_self_orientation_result` must preserve the selected
self-orientation result id, path, version, resolver module, and outcome.

`locked_orientation_basis` must preserve the basis asserted by the request and
verified against the self-orientation result.

`selected_reentry_request` must preserve the request as evaluated, including
its declared next step, bounds, hierarchy constraints, requested permissions,
non-claims, and refusal acknowledgement.

`reentry_admissibility_checks` must show the bounded checks actually used.

`reentry_admissibility_basis` must explain only why this one request was
admitted or blocked. It must not become a roadmap, recap, or authority surface.

`non_claims` must remain explicit and false where the result carries false
posture. In particular, the result must not claim authority creation,
continuity completion, final governance, final system identity, standing
upgrade, source replacement, derivative authority upgrade, general permission,
or follow-on authorization.

## 12. What Remains Preserved

After admission or refusal:

- the self-orientation artifact remains preserved
- the locked basis remains preserved
- the request remains preserved
- upstream current, governing, current-state, continuity, derivative, API, and
  operator-facing artifacts remain preserved
- source remains source
- derivative remains derivative
- operator-facing derivative remains operator-facing derivative
- open remains open
- blocked or refused remains visible when selected
- admission for one step does not authorize the next step
- refusal does not rewrite the self-orientation result
- refusal does not rewrite upstream current-state or continuity posture

The gate is additive. It does not mutate prior artifact families.
