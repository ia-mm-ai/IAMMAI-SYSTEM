# BODY SIGNAL SCOPE V0 MIN SPEC

## 1. Purpose

This file defines the first bounded body-signal scope spec for the present
`IAMMAI-SYSTEM` execution line.

Body-signal acceptance now stands. One live `SIGNAL_ACCEPTED` result accepted
the recognized `BODY_PASS_SIGNAL` into `current_signal_recognition_standing`.
Current self-orientation v4 now recognizes that accepted-signal posture as
downstream and non-operative.

The next constitutional distinction is acceptance versus scope.

Recognition says one candidate indication qualifies as body-relevant signal.
Acceptance says one `SIGNAL_RECOGNIZED` result may enter one declared bounded
matter for structured handling. Scope says what one accepted signal is
applicable to inside that declared matter, and what it is not applicable to.

The first scoped applicability is
`current_signal_recognition_standing__body_pass_signal_nonoperative_posture_scope`.
This means the accepted `BODY_PASS_SIGNAL` applies only as bounded evidence
that the v0 body-pass result can be recognized and accepted as non-operative
body-signal posture inside `current_signal_recognition_standing`.

This file does not define signal presence, signal threshold, signal truth,
signal use, signal routing, an event bus, workflow, action authorization,
roadmap generation, general continuation, governance, or a body relevance
medium implementation.

## 2. Status and Rank

This is an additive v0-min signal-scope spec for the present execution line
only.

It ranks below constitutional and reference authority surfaces, including the
preserved `reference/IAMMAI/` surfaces and the current executable source,
tests, artifacts, and standing result surfaces already present in this

This spec does not create authority. It does not define final governance. It
does not complete continuity. It does not complete final system identity. It
does not replace current executable source, tests, artifacts, body-signal
boundary, body-signal recognition, body-signal acceptance, current
self-orientation v4, or any standing result surface.

Scope through this surface is preparation-side applicability containment only.
It is not presence, threshold, truth, action, permission, routing, workflow,
signal use, or body-wide signaling.

## 3. Why This Spec Is Needed Now

The body can now recognize a signal. The body can now accept that signal into
a declared matter. Accepted signal is not yet scoped signal.

Without scope, accepted signal may later bleed beyond the matter it entered.
Without a bounded scope surface, accepted signal may drift into permission,
currentness, action, routing, workflow, body-wide applicability, or inflated
medium language.

Therefore one bounded body-signal scope spec is lawful before any resolver is
built. This is not because signal must be used. It is because accepted signal
now needs declared applicability if it is to remain contained.

## 5. Body-Signal Scope Surface

This spec applies only to one `SIGNAL_ACCEPTED` result and one bounded
signal-scope request.

It decides scoped applicability or blocking for that one accepted signal only.
It only bounds applicability inside the declared matter.

It does not:

- establish presence
- establish threshold
- create truth
- create action permission
- route signals
- use signals
- aggregate signals
- create priority
- create scheduling
- create storage semantics
- create a signal bus
- create an event bus
- create regulation
- create workflow
- create a next-step generator
- authorize action
- authorize follow-on work
- create general continuation
- mutate prior artifacts
- overwrite upstream surfaces
- explain the repository for outsiders

Scope is containment of applicability. It is not use, action, routing,
standing-state formation, or permission.

## 6. Required Input Pair

Body-signal scope requires exactly two inputs:

1. one `SIGNAL_ACCEPTED` result
2. one bounded signal-scope request declaring the applicability boundary inside
   the accepted matter

Both inputs are required.

A blocked signal-acceptance result cannot be scoped. An accepted signal does
not automatically become scoped. A scope request does not grant itself scope.

The accepted matter must be preserved. The scope boundary must be bounded and
explicit.

For this first spec, the only supported accepted matter is
`current_signal_recognition_standing`, and the only supported scope is
non-operative body-pass signal posture inside that matter.
