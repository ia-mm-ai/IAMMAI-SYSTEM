## 4. Definitions

`command_implementation_boundary` means a bounded review surface that defines conditions for a possible future checker-only portable verification command implementation. It is not command implementation.

`checker_only_command_implementation` means future code may only inspect declared evidence and report bounded findings if separately implemented under a later boundary. It may not transfer, migrate, receive, authorize, deploy, host, publish, currentize, complete, continue, create reusable permission, authorize derivative reception, authorize vessel relation, authorize another reception request, or authorize follow-on work.

`command_implementation_candidate` means a future implementation-shaped surface named for boundary review only. A command implementation candidate is not an implemented command, script, CLI, executable entrypoint, invocation, output, result, or success.

`command_execution` means actually running a command or creating an execution event. Command execution remains future work and requires a separate boundary.

`command_invocation` means an actual command call, instructed run, CLI call, script call, workflow call, or comparable operational trigger. This boundary does not create command invocation.

`command_output` means data emitted by a command after execution. This boundary does not create command output, and future command output must not become source, authority, currentness, operation permission, public readiness, final completion, continuation, reusable permission, or follow-on authorization.

`command_result` means any future bounded report object produced by a separately specified and separately executed checker command. This boundary does not create a command result.

`command_success` means a future command's successful exit, passed checks, completed run, or comparable execution success. Command success must not create source, authority, currentness, operation permission, public readiness, final completion, continuation, reusable permission, derivative reception, vessel relation, another reception request, or follow-on work.

`bounded_command_report` means a future non-authoritative report that may state bounded check findings if a checker-only command is separately implemented and separately authorized to run. It is not source, authority, currentness, final completion, public readiness, operation permission, or continuation.

`command_output_non_authority` means future command output may be reportable evidence only if separately implemented and executed, and it must not become governing authority.

`command_success_non_currentness` means future command success must not make a repository copy, local path, artifact, evidence surface, carrier, archive, vendor account, OS, device, environment, or narration current.

`command_success_non_final_completion` means future command success must not claim final completion, public readiness, operation permission, continuation, reusable permission, or follow-on authorization.

`contained_reference_shaped_input` means future implementation inputs must preserve selected prior results by bounded reference-shaped summaries rather than recursively embedding full upstream artifact bodies.

`evidence_manifest_dependency` means a future checker-only command implementation must depend on declared evidence-manifest basis and must not invent undeclared source, authority, currentness, or evidence classes.

`implementation_non_claim` means an explicit false posture preserving that this boundary did not implement, execute, authorize execution, invoke, emit output, create success, deploy, host, publish, transfer, migrate, receive, currentize, complete, continue, or authorize follow-on work.

`execution_requires_separate_boundary` means any future command execution must begin from a separate bounded specification and cannot be inferred from this command implementation boundary.

Command implementation boundary is not command implementation.

Checker-only implementation means future code may only inspect declared evidence and report bounded findings if separately implemented.

Command output must not become source.

Command success must not become currentness or final completion.

Command execution remains future and separately bounded.
