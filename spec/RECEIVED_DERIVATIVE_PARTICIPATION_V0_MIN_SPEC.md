# Received Derivative Participation V0-Min Spec

## 1. Purpose

This file defines the first bounded received-derivative participation surface for the v0-min coexistence execution line.

It derives from the current-state subsystem, the current-state admissibility / touch-permission bridge, the continuity-transfer unit, and the continuity-transfer receipt surface now standing in this repository line.

The pressure answered here is narrow: after a carried derivative has been lawfully received, who or what may use it, in what bounded ways, without silently promoting it into source, authority, local standing, or continuity completion.

This file is about lawful post-receipt use. It is not another current-state query surface, transfer mechanic, receipt mechanic, replay path, merge path, persistence layer, registry doctrine, final participation law, final governance framework, final continuity doctrine, or minimum lawful system declaration.

The next forced pressure is post-receipt participation, not a giant abstract participation doctrine.

## 2. Status and Rank

This spec ranks below the constitutional and reference authority surfaces under `reference/IAMMAI/`.

It is additive to the present executable line. It does not replace the canonical executable source, the tests, the emitted artifacts, the current-state surfaces, the touch-permission bridge, the continuity-transfer unit, or the continuity-transfer receipt surface.

It does not define final governance, final participation law, final continuity completion, final system identity law, full operator doctrine, full vessel doctrine, or intelligence participation law.

It is a bounded participation spec for the present v0-min coexistence execution line only.

## 3. Why This Spec Is Needed Now

The repository can now resolve current execution authority, preserve run family and status, resolve current governing posture, resolve effective family, consume that effective family, resolve current work, emit current-state surfaces, admit bounded touch, transfer a carried derivative across a seam, and receive that carried derivative at a receiving boundary.

That makes downstream post-receipt use materially possible.

Without a bounded participation surface, a received derivative can still be silently treated as source, governing authority, local-state completion, continuity completion, or implicit standing.

Therefore this spec defines the smallest received-derivative participation surface needed before downstream use can scale lawfully.

## 5. What a Received Derivative Means Here

A received derivative is a carried derivative that has passed a bounded continuity-transfer receipt surface with outcome `RECEIVED`.

It is not source. It is not governing authority. It is not final local identity. It is not continuity completion. It is not a replacement for the selected source surface, the transfer unit, the receipt result, or the preserved artifact chain that made it readable.

In this bounded slice:

- the selected source surface remains source
- the transfer artifact remains transfer lineage
- the receipt artifact remains receipt lineage
- the received payload remains carried derivative
- the received derivative may become available only for bounded downstream use

Participation must not silently collapse source, transfer, receipt, and received derivative into one undifferentiated local state.

## 6. What Participation Means Here

Participation here means bounded use of a received derivative under explicit participant-class, use-class, lineage, payload-scope, and non-claim checks.

It may allow inspection, reference, or one bounded downstream derivative formed from received fields and references already preserved by the receipt result.

Participation here is not:

- constitutional authorship
- governing standing
- source identity
- host replay
- preserved-run merge
- mutation of preserved artifacts
- continuity completion
- final participation law
- unrestricted downstream freedom

Participation does not grant authority merely because a received derivative arrived at a receiving boundary.

## 7. Participation Source Surface

The participation source must be one already-emitted continuity-transfer-receipt result with outcome `RECEIVED`.

The selected receipt result must preserve, where applicable:

- selected receipt result identity and path
- selected transfer result identity
- selected source-surface identity
- selected source-surface family and outcome
- touch-permission lineage
- received payload
- derivative status
- source/derivative distinction
- carried non-claims

Blocked, malformed, unsupported, unreadable, or non-received receipt artifacts do not drive participation.

Participation must not infer admissibility from latest current-state, authority, family, status, governing, transfer, or receipt files alone.

## 8. Participant Classes

The first bounded participant classes are:

- `LOCAL_READER_PARTICIPANT`
- `LOCAL_DERIVATION_PARTICIPANT`

`LOCAL_READER_PARTICIPANT` may inspect or reference a received derivative within the admitted participation payload scope. It may not mutate preserved artifacts, replay the host, merge runs, promote the received derivative into source, or claim authority.

`LOCAL_DERIVATION_PARTICIPANT` may produce one bounded downstream derivative from received fields and references already exposed by the selected receipt result. It may not promote that downstream derivative into source, governing authority, final continuity, or local standing.

These are engineering-side bounded participation labels for this execution line. They are not constitutional castes, final roles, operator doctrine, vessel doctrine, or intelligence participation law.

## 9. Use Classes

The first bounded use classes are:

- `READ_PARTICIPATION`
- `REFERENCE_PARTICIPATION`
- `DERIVATIVE_PARTICIPATION`

`READ_PARTICIPATION` allows bounded inspection of selected receipt metadata, selected transfer lineage, selected source-surface identity, received payload fields, received references, checks, and non-claims already exposed by the receipt result.

`REFERENCE_PARTICIPATION` allows bounded carrying or citing of selected receipt identity, selected transfer identity, selected source-surface identity, received references, and non-claims already exposed by the receipt result.

`DERIVATIVE_PARTICIPATION` allows one bounded downstream derivative to be formed only from received fields and references already exposed by the receipt result and admitted by the participation request.

All use classes refuse:

- replay
- merge
- mutation of preserved artifacts
- source replacement
- authority promotion
- continuity completion
- standing upgrade
- final identity claims

## 10. Participation Payload Scope

The smallest lawful participation payload may include only:

- selected receipt result identity and path
- selected transfer result identity where preserved
- selected source-surface identity, family, and outcome where preserved
- bounded received fields
- bounded received references
- carried non-claims
- participant class
- use class
- participation basis
- explicit derivative status of the participation payload

The participation payload must not silently include:

- hidden provenance not already exposed
- replay authority
- merge authority
- mutation authority
- constitutional authority
- governing authority
- final identity claims
- continuity completion claims
- source replacement
- latest-file inference

The selected receipt result remains the receipt source for participation. The selected source surface remains source. The participation payload remains derivative / bounded-use lineage.

## 11. Participation Preconditions

Before participation may begin:

- a successful continuity-transfer-receipt result must already exist
- the selected receipt result must have outcome `RECEIVED`
- the selected receipt result must preserve source/derivative distinction
- the selected receipt result must preserve selected transfer lineage
- the selected receipt result must preserve selected source-surface identity
- the selected receipt result must preserve touch-permission lineage where applicable
- the selected receipt result must preserve carried non-claims
- the participation request must name a supported participant class
- the participation request must name a supported use class
- the requested participation fields must stay within the received carried fields and references

Participation does not bypass receipt. It builds on the receipt surface rather than replacing it.

## 12. Participation Checks

A future resolver must perform at least these checks before emitting a `PARTICIPATED` result:

- selected receipt result exists and is readable
- selected receipt result has supported successful outcome `RECEIVED`
- selected receipt result is within participation scope
- received payload is readable and coherent
- received payload preserves explicit derivative status
- `source_remains_source` remains true
- `carried_derivative_remains_derivative` remains true
- selected source-surface identity remains preserved
- selected transfer result identity remains preserved
- touch-permission lineage remains readable and coherent where applicable
- effective authority, family, status, and governing references remain readable and coherent where the participation result depends on them
- canonical core execution file remains aligned with `src/integrity_host_v0_min_coexistence_v2.py`
- effective currentness references remain internally coherent
- bounded non-claims remain false
- participation payload scope stays within the received carried fields and references
- participation does not silently fall back to stale prior-family artifacts
- participation does not infer current state from latest files alone
- participant class is one of the bounded supported participant classes
- use class is one of the bounded supported use classes
- participation preserves source/derivative distinction
- participation refuses replay, merge, mutation, continuity completion, standing upgrade, and source replacement

Checks should be explicit enough for a result artifact to show what was admitted or refused without creating a broad schema engine.

## 14. Future Participation Result Artifact

A future implementation should emit one bounded participation result artifact. At minimum it must preserve:

- participation result id
- participation result type and version
- `generated_at`
- selected receipt result path and id used
- selected transfer result id where preserved
- selected source-surface id and family where preserved
- participant class
- use class
- participation basis
- received payload fields selected for participation
- outcome: `PARTICIPATED` or `REFUSED`
- block code and block reason if refused
- checks or bounded check summary
- carried-forward non-claims

  selected_receipt_result_id
  selected_receipt_result_type

  receipt_basis

  selected_transfer_result_path

  transfer_basis

  selected_source_surface_path
  selected_source_surface_id

  selected_source_surface_outcome

  received_derivative_participation_request_id

  value: PARTICIPATED | REFUSED

  block_code

For `PARTICIPATED`, the result should preserve only the bounded participation fields admitted for use and the provenance showing their receipt lineage.
