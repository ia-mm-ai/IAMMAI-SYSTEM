## 8. Terminal Outcome Family and Precedence

The exact specification-governed terminal outcome family is:

1. `DESCENDANT_BODY_CREATION_OPERATION_BLOCKED`
2. `DESCENDANT_BODY_CREATION_OPERATION_REQUIRES_BOUNDARY_ALLOWANCE`
3. `DESCENDANT_BODY_CREATION_OPERATION_NOT_CREATED`
4. `DESCENDANT_BODY_CREATION_OPERATION_CREATED`

Precedence is exactly the order above:

1. structural, control, identity, binding, ownership, route, history, attribution, prohibited-posture, or non-claim failure produces `BLOCKED`;
2. a separately bounded operation request whose boundary allowance is genuinely missing or insufficient under mature family law may produce `REQUIRES_BOUNDARY_ALLOWANCE`;
3. an exact allowed event whose ordinary support is not exactly Boolean true produces `NOT_CREATED`;
4. an exact allowed event with exact ordinary support true produces `CREATED`.

The historical executable-only outcome `DESCENDANT_BODY_CREATION_OPERATION_NOT_RECORDED` is not specification-governed and must not enter the V2 family.

This specification creates no `REQUIRES_ADDITIONAL_BASIS`, `NOT_PERFORMED`, or other outcome.

For the exact closed `_001` event governed here, no supplied input path lawfully allocates to `REQUIRES_BOUNDARY_ALLOWANCE`. The current V3 allowance is part of the constitutional event key. Its absence, mutation, or substitution is event corruption and must produce `BLOCKED`. `REQUIRES_BOUNDARY_ALLOWANCE` remains mature family law for another separately bounded operation request with genuinely insufficient allowance; this specification neither invents nor allocates such another request.

No caller may select an outcome.
