# Continuity Transfer Unit V0-Min Spec

## 1. Purpose

This file defines the first bounded continuity-transfer-unit spec for the v0-min coexistence execution line.

It derives from the current-state subsystem now standing in this repository and from the current-state admissibility / touch-permission bridge:

- current execution-authority resolution
- preserved-run family packet
- preserved-run status packet
- current-governing packet
- governing transition
- governing re-resolution
- successor-family adoption
- effective-family resolution
- effective-family consumption
- current-work-input resolution
- current-work-operation completion
- current-state readout, handoff, export, delivery, application, and answer/read
- generic current-state query
- concrete current-state "what stands now"
- concrete current-state "what remains open"
- current-state admissibility and touch-permission

This spec is about lawful transfer across seams, carriers, or containers. It is not more current-state querying, not another answer profile, and not a broader interface layer.

The next forced pressure is continuity-transfer: a current-state surface that is lawful to touch must still be carried across a seam without silent mutation, collapse, or narrator-dependent memory.

This file does not define final governance, final continuity completion, final system identity, replay law, merge law, persistence architecture, registry doctrine, or a broad continuity framework for the whole body.

## 2. Status and Rank

This spec ranks below the constitutional and reference authority surfaces under `reference/IAMMAI/`, including the constitutional protocol, implementation overviews, runtime contract surfaces, and architecture surfaces.

It does not define final governance.

It is a bounded continuity-transfer spec for the present v0-min coexistence execution line only.

## 3. Why This Spec Is Needed Now

The repository can now resolve, answer, query, concretize, and lawfully touch current-state surfaces.

That makes current-state use materially possible. A downstream surface can now ask for a bounded touch class and receive an explicit admission or refusal without pretending that read access is governance, replay, merge, or continuity completion.

But use across seams still has a separate risk. Without one bounded transfer unit, a current-state surface can be carried by ad hoc narration, manual recap, or silent reinterpretation. That would make the seam depend on memory performance rather than on an emitted artifact with explicit source, derivative status, checks, and non-claims.

A narrow transfer spec is therefore required before the current-state subsystem can be carried across container, carrier, or execution-boundary changes lawfully.

## 5. What a Continuity-Transfer Unit Means Here

A continuity-transfer unit is the smallest lawful carried packet that can move a selected current-state surface across a seam, carrier, or container boundary while preserving source identity, provenance, derivative status, checks, and non-claims.

It is not full history.

It is not a giant recap.

It is not whole-body reintroduction.

It is not whole continuity doctrine.

It is not narrator memory.

It is not a replay of the host.

It is not a merge of preserved runs.

It carries only what must survive the seam for lawful downstream continuation:

- the selected source surface identity
- the selected source surface family and outcome
- the selected source surface path
- the touch/admissibility basis that permitted the relevant use
- the bounded carried payload
- the explicit source-vs-derivative relation
- the carried non-claims

Source remains source. Transferred material remains derivative / carried. Transfer does not silently replace the origin surface. Transfer does not claim continuity completion.

## 6. Transfer Source Surface

A transfer source must be an already-emitted successful current-state surface.

Where scaling use is involved, the selected surface must also have already passed current-state admissibility / touch-permission for the intended use being transferred.

The first bounded admissible source set is:

- admitted-for-touch current-state answer/read result
- admitted-for-touch current-state query result
- admitted-for-touch current-state "what stands now" result
- admitted-for-touch current-state "what remains open" result

The selected source surface must remain readable and must expose a supported successful outcome:

- `ANSWERED`
- `ANSWERED_QUERY`
- `ANSWERED_WHAT_STANDS_NOW`
- `ANSWERED_WHAT_REMAINS_OPEN`

Blocked, malformed, unsupported, non-successful, or non-admitted current-state surfaces do not drive transfer.

## 7. Transfer Classes

The first bounded transfer classes are:

- `REFERENCE_TRANSFER`
- `DERIVATIVE_TRANSFER`

`REFERENCE_TRANSFER` may carry bounded source identity, source path, result family, outcome, provenance, effective references where exposed, touch-permission reference, transfer basis, and non-claims.

`DERIVATIVE_TRANSFER` may carry one bounded derivative packet formed only from fields already exposed by the selected source surface and already admitted by the touch-permission result for derivation or reference use.

Both transfer classes refuse:

- replay
- merge
- mutation
- continuity completion
- hidden standing upgrade
- source replacement
- hidden authority promotion
- final identity claims

No broader transfer taxonomy is defined here.

## 8. Transfer Payload Scope

The smallest lawful transfer payload may include:

- selected source surface identity
- selected source surface path
- selected source surface family
- selected source surface outcome
- selected source surface effective references where exposed
- selected source surface summary fields where already exposed
- selected source surface answered fields where already exposed
- carried non-claims
- explicit transfer basis
- explicit transfer class
- explicit derivative status of the payload
- touch/admissibility result identity and path where applicable

The payload must keep source and derivative fields distinguishable. A carried value should be marked as carried from the selected surface, not re-declared as newly governing source state.

The payload must not silently include:

- hidden provenance not already exposed
- replay authority
- merge authority
- mutation authority
- final identity claims
- continuity completion claims
- constitutional authority
- protocol authorship
- latest-file inference
- stale prior-family fallback

## 9. Admissibility and Touch Preconditions

Before transfer may begin:

- the selected current-state surface must be admissible
- the requested touch must already be admitted for the use being transferred
- the touch-permission result must identify the selected current-state surface
- the touch-permission result must preserve the admitted touch class
- the transfer request must stay within the admitted touch scope
- the selected surface and the touch-permission result must remain readable

Continuity-transfer does not bypass admissibility / touch-permission. It builds on that bridge.

If no successful touch/admissibility result exists for the intended transfer use, the transfer must be refused.

## 10. Transfer Checks

A bounded continuity-transfer unit may be emitted only when all minimum checks pass:

- selected source surface exists and is readable
- selected source surface has a supported successful outcome
- selected source surface is within transfer scope
- required touch/admissibility result exists and is readable where required
- touch/admissibility outcome is successful for the intended transfer use
- touch/admissibility result corresponds to the selected source surface
- transfer request stays within the admitted touch scope
- effective authority, family, status, and governing references remain readable and coherent where the source surface depends on them
- canonical core execution file remains aligned with `src/integrity_host_v0_min_coexistence_v2.py`
- effective currentness references remain internally coherent
- effective authority, family, status, and governing artifacts name the same current governing source run where those surfaces expose it
- effective authority, family, status, and governing artifacts name the same current governing ingress run where those surfaces expose it
- bounded non-claims remain false
- transfer payload scope stays within already exposed and already admitted fields
- transfer does not silently fall back to stale prior-family artifacts
- transfer does not infer current state from latest files alone
- transfer class is one of the bounded supported transfer classes
- transfer preserves source/derivative distinction
- transfer refuses replay, merge, mutation, continuity completion, standing upgrade, and source replacement

These checks are implementation-facing. They define the minimum gate for one transfer unit, not a general continuity system.

## 11. Refusal / Block Conditions

Continuity-transfer refusal must remain explicit. It is a bounded transfer refusal, not a global constitutional condemnation.

At minimum, transfer must refuse for:

- no admissible source surface available
- unreadable selected source surface
- malformed selected source surface
- blocked selected source surface
- unsupported source surface
- non-successful source surface outcome
- no successful touch/admissibility result for the intended use where required
- unreadable touch/admissibility result
- malformed touch/admissibility result
- touch/admissibility result does not correspond to the selected source surface
- canonical execution line mismatch
- effective reference incoherence
- stale prior-family fallback attempted
- latest-file inference attempted
- replay shortcut attempted
- merge shortcut attempted
- continuity-completion shortcut attempted
- silent standing upgrade attempted
- implicit mutation attempted
- implicit authority claim attempted
- transfer class out of scope
- transfer payload out of scope
- hidden source replacement attempted
- derivative/source distinction collapse attempted
- multiple source surfaces conflict without explicit bounded selection

A refused transfer should preserve the selected source surface identity where available, the touch/admissibility reference where available, the transfer request, the block code, the block reason, bounded check details, and carried non-claims.

## 12. Future Transfer Result Artifact

A future bounded implementation should emit one continuity-transfer result artifact.

The smallest useful result artifact preserves:

- transfer result id
- transfer result type
- transfer result version
- generated_at
- resolver module or emitting surface
- selected source surface path used
- selected source surface id used
- selected source surface family
- selected source surface outcome
- transfer class
- transfer basis
- touch/admissibility result path used where applicable
- touch/admissibility result id used where applicable
- transfer payload
- outcome: `TRANSFERRED` or `REFUSED`
- block code and block reason if refused
- checks or bounded check summary
- carried-forward non-claims

A calm implementation-facing artifact shape is:

```text
continuity_transfer_metadata:
  continuity_transfer_result_id: string
  continuity_transfer_result_type: continuity_transfer_unit
  continuity_transfer_result_version: v0-min
  generated_at: string
  resolver_module: string

selected_source_surface:
  selected_source_surface_path: string
  selected_source_surface_id: string
  selected_source_surface_family: string
  selected_source_surface_outcome: string
  selected_source_surface_effective_references: object

touch_permission_reference:
  touch_permission_result_path: string | null
  touch_permission_result_id: string | null
  admitted_touch_class: string | null
  admitted_touch_scope: object | null

transfer_request:
  continuity_transfer_request_id: string
  transfer_class: REFERENCE_TRANSFER | DERIVATIVE_TRANSFER
  transfer_basis: string
  requested_transfer_fields: list[string]
  target_seam_label: string

checks:
  - check_name: string
    passed: boolean
    expected_posture: any
    actual_posture: any

outcome: TRANSFERRED | REFUSED

block:
  block_code: string | null
  block_reason: string | null

transfer_payload:
  payload_derivative_status: carried_derivative
  source_remains_source: true
  carried_fields: object
  carried_references: object

transfer_summary:
  transferred_field_count: integer
  transferred_field_names: list[string]
  source_surface_id: string | null
  touch_permission_result_id: string | null

non_claims:
  continuity_completed: false
  standing_upgraded: false
  replayed_into_live_host: false
  merged_into_local_state: false
  minimum_lawful_system_completed: false
  final_system_identity_completed: false
  final_governance_completed: false
  final_continuity_transfer_completed: false
```

For `TRANSFERRED`, the result should preserve only the bounded payload fields admitted for transfer and the provenance showing their source.

For `REFUSED`, the result should preserve no transfer payload beyond refusal context and carried non-claims.

This shape is an implementation target, not protocol law and not a persistence architecture.
