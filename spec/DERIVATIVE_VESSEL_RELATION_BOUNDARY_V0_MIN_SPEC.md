# DERIVATIVE VESSEL RELATION BOUNDARY V0 MIN SPEC

## 1. Purpose

This file defines the first bounded derivative-vessel relation boundary spec
for the present `IAMMAI-SYSTEM` execution line.

Bounded derivative current-state read and bounded operator-facing terminal
brief output already stand in narrow form. The next architectural pressure is
not another vessel implementation or another operator surface. The next
pressure is relation boundary:

`How may a derivative vessel relate to the body without becoming source,
authority, currentness, permission, ownership, adoption, validation, or
privileged standing?`

A derivative vessel relation is a downstream relation in which a vessel may
read, carry, render, or emit bounded derivative material from already-standing
body surfaces while preserving that the body/source surfaces remain upstream.

This file defines that relation as downstream and bounded. It does not
implement a vessel, define deployment, create an operator integration, define
a current-state reader, define an operator brief, create governance, create
permission, create adoption, create public release standing, create privileged
standing, complete final system identity, or define persistence/registry law.

## 2. Status and Rank

This spec ranks below constitutional and reference authority surfaces,
including the preserved `reference/IAMMAI/` surfaces, the current executable
source, the tests, and the emitted artifacts already standing in the
repository.

It is additive. It does not create authority. It does not define final
governance. It does not complete continuity. It does not complete final system
identity. It does not replace current executable source, tests, artifacts,
self-orientation results, body-signal results, derivative vessel results, or
operator-facing brief results.

It is a bounded relation-boundary spec for the present execution line only.
It does not open general vessel recognition and does not make derivative
output current, governing, permissive, authoritative, adopted, or privileged.

## 3. Why This Spec Is Needed Now

Current self-orientation can now recognize standing downstream surfaces while
preserving that current and governing basis remain upstream-derived.

The re-entry and body-signal lines have proven single-step intake, closure,
non-operative posture, and non-collapse across recognition, acceptance, and
scope.

Bounded derivative vessel read/output has already occurred in narrow form, and
one bounded operator-facing terminal brief now stands as a downstream render
over a derivative vessel result.

Without a derivative vessel relation boundary, future vessel work could
confuse carriage with source, output with authority, rendering with
currentness, or availability with standing. It could also confuse an operator-
facing render with source, permission, adoption, or validation.

Therefore one bounded derivative-vessel relation boundary spec is lawful
before any broader vessel relation is recognized or implemented.

## 4. What Now Stands

The standing surfaces relevant to this relation boundary include:

- current self-orientation v5
- bounded current-state surfaces
- re-entry admissibility and re-entry receipt
- body-signal recognition, acceptance, and scope
- bounded derivative current-state read
- bounded operator-facing terminal brief
- carried non-claims that remain false

This is not a whole-body recap. These surfaces are named only because a
derivative vessel relation must preserve source/body, derivative, operator-
facing, re-entry, signal, and non-claim distinctions.

## 5. Derivative Vessel Relation Scope

This spec applies only to relation between already-standing body surfaces and
a downstream derivative vessel.

It defines relation boundary, not implementation. It preserves that:

- body/source surfaces remain upstream
- vessel outputs remain downstream
- operator-facing outputs remain downstream of derivative output
- source/derivative distinction remains visible
- currentness remains upstream-derived
- relation recognition remains additive

It does not recognize a vessel as source. It does not recognize a vessel as
authority. It does not recognize a vessel as currentness source. It does not
recognize a vessel as permission source. It does not recognize a vessel as an
adoption path. It does not recognize a vessel as validation of the body. It
does not recognize a vessel as final governance. It does not mutate prior
artifacts. It does not define general orchestration. It does not create public
release standing. It does not explain the repository for outsiders.

## 6. Required Relation Basis

A future implementation would need at least the following basis before
recognizing a derivative vessel relation:

1. one standing current self-orientation result
2. one standing source/current-state surface used as derivative basis
3. one derivative vessel result or candidate relation artifact
4. one declaration of relation bounds
5. carried non-claims

The derivative vessel relation must be anchored in standing source/body
surfaces. The vessel cannot name itself as source. The vessel cannot select
currentness by recency. The vessel cannot replace provenance, rank, status, or
currentness assigned by local shell surfaces. The vessel cannot create
permission by successful output.

If the standing source/body basis is absent, unreadable, malformed, blocked,
or not preserved by the derivative vessel result, the relation cannot be
recognized.

## 7. Derivative Vessel Relation Declaration Shape

The derivative vessel relation declaration is a candidate for relation
recognition. It is not permission and does not authorize itself.

### 7.1 `derivative_vessel_relation_metadata`

The declaration must preserve:

- `derivative_vessel_relation_id`
- `derivative_vessel_relation_type`
- `derivative_vessel_relation_version`
- `declared_at`
- `declared_by_surface`

`declared_by_surface` records where the relation was declared. It does not
imply authority.

### 7.2 `source_body_basis`

The declaration must preserve:

- `self_orientation_result_path`
- `self_orientation_result_id`
- `self_orientation_outcome`
- `source_surface_path`
- `source_surface_id`
- `source_surface_family`
- `source_surface_outcome`
- current, governing, and effective reference paths where exposed

Required posture:

- source/body basis must stand before derivative vessel relation can be
  recognized
- source/body basis must remain upstream
- source/body basis must not be selected by latest-file recency
- source/body basis must not be replaced by vessel output

### 7.3 `derivative_vessel_basis`

The declaration must preserve:

- `derivative_vessel_result_path`
- `derivative_vessel_result_id`
- `derivative_vessel_result_type`
- `derivative_vessel_result_outcome`
- `derivative_vessel_module`
- `derivative_output_family`
- `derivative_output_basis`

Required posture:

- derivative vessel output must preserve source basis
- derivative vessel output must remain derivative
- derivative vessel output must not assign its own authority, rank,
  currentness, provenance, status, permission, or standing beyond what the
  local shell permits

### 7.4 `declared_relation_bounds`

The declaration must preserve:

- `relation_is_downstream`
- `source_basis_preserved`
- `derivative_output_preserved`
- `operator_facing_output_downstream_if_present`
- `relation_reversible`
- `relation_additive_only`
- `no_source_replacement`
- `no_authority_creation`
- `no_currentness_creation`
- `no_permission_creation`
- `no_adoption_creation`
- `no_privileged_standing`
- `no_final_governance_completion`
- `no_final_system_identity_completion`

Required posture:

- all relation-preserving fields must hold
- all no-claim fields must remain true as declarations
- all created-outcome counterparts must remain false in emitted results

### 7.5 `hierarchy_constraints`

The declaration must preserve:

- `vessel_allowed_as_source`
- `vessel_allowed_as_authority`
- `vessel_allowed_as_currentness_source`
- `vessel_allowed_as_permission_source`
- `vessel_allowed_as_adoption_path`
- `vessel_allowed_as_public_release`
- `vessel_allowed_as_final_governance`
- `operator_surface_allowed_as_source`
- `derivative_output_allowed_to_replace_source`
- `latest_file_recency_allowed`

Required posture: all of these must be `false`.

### 7.6 `correspondence_requirements`

The declaration must preserve:

- `must_preserve_source_identity`
- `must_preserve_source_outcome`
- `must_preserve_derivative_basis`
- `must_preserve_source_derivative_distinction`
- `must_preserve_operator_downstream_distinction`
- `must_preserve_non_claims`
- `must_prevent_over_mirroring`
- `must_prevent_under_mirroring`

Required posture: all of these must be `true`.

### 7.7 `declared_non_claims`

The declaration must preserve these explicit true non-claims:

- `does_not_create_authority = true`
- `does_not_create_permission = true`
- `does_not_create_currentness = true`
- `does_not_replace_source_surface = true`
- `does_not_upgrade_derivative_to_source = true`
- `does_not_upgrade_operator_to_source = true`

## 8. Relation Boundary Requirements

A derivative vessel relation must satisfy these minimum requirements:

- relation must be explicit
- relation must be bounded
- relation must identify the source/body basis
- relation must identify the derivative vessel basis
- relation must preserve source/derivative distinction
- relation must preserve operator-facing distinction where present
- relation must remain additive
- relation must be reversible or non-standing by default
- relation must not create private or privileged standing
- relation must not create adoption
- relation must not create currentness
- relation must not create authority
- relation must not create permission
- relation must not create final governance
- relation must not complete final system identity
- relation must not complete continuity
- relation must not replace source

This first spec does not open general vessel recognition. Future specific
relation types may require successor specs.

- derivative vessel result preserves source basis

- relation declaration is present
- relation declaration is well-formed
- source identity is preserved
- source outcome is preserved
- derivative basis is preserved
- source/derivative distinction is preserved
- operator/downstream distinction is preserved
- relation is additive only
- relation does not create authority
- relation does not create permission
- relation does not create currentness
- relation does not create adoption
- relation does not create privileged standing
- relation does not replace source
- relation does not complete final governance
- relation does not complete final system identity
- relation does not complete continuity

## 11. Result Artifact

A future implementation would need to emit one bounded result artifact with at
least these top-level sections:

- `derivative_vessel_relation_boundary_metadata`
- `selected_source_body_basis`
- `selected_derivative_vessel_basis`
- `selected_relation_declaration`
- `relation_boundary_checks`
- `outcome`
- `block`
- `recognized_derivative_vessel_relation`
- `derivative_vessel_relation_boundary_basis`
- `non_claims`

Minimum metadata:

- `derivative_vessel_relation_boundary_result_id`
- `derivative_vessel_relation_boundary_result_type`
- `derivative_vessel_relation_boundary_result_version`
- `generated_at`
- `resolver_module`

Minimum outcome family:

- `DERIVATIVE_VESSEL_RELATION_RECOGNIZED`
- `BLOCKED`

For `DERIVATIVE_VESSEL_RELATION_RECOGNIZED`, the result must preserve:

- source/body basis id, path, and outcome
- derivative vessel result id, path, and outcome
- derivative output family
- relation id and type
- downstream status
- additive-only status
- source-preserved status
- derivative-preserved status
- operator-downstream status where present
- no-authority status
- no-permission status
- no-currentness status
- no-adoption status
- no-privileged-standing status
- no-source-replacement status
- no-final-governance status
- no-final-system-identity status
- no-continuity-completion status

For `BLOCKED`, the result must preserve selected source/body basis where
available, selected derivative vessel basis where available, selected relation
declaration where available, block code/reason, failed checks, and
non-claims.

## 12. What Remains Preserved

After derivative vessel relation recognition or blocking:

- source/body basis remains preserved
- derivative vessel result remains preserved
- operator-facing output remains preserved where present
- relation declaration remains preserved where available
- recognized relation result remains additive
- source remains source
- derivative remains derivative
- operator-facing remains downstream
- relation remains relation only
- recognized relation does not create authority
- recognized relation does not create permission
- recognized relation does not create currentness
- recognized relation does not create adoption
- recognized relation does not create privileged standing
- recognized relation does not replace source
- recognized relation does not authorize follow-on vessel relations

Relation recognition may preserve that a derivative vessel can carry or render
bounded derivative material. It may not convert that relation into source,
authority, permission, currentness, adoption, validation, ownership, or
privileged standing.

## 15. Closing Boundary Statement

The body/source surfaces remain upstream.

A derivative vessel relation is downstream and bounded.

A derivative vessel may carry or render bounded derivative material only
within declared relation bounds.

Relation recognition does not create authority, permission, currentness,
adoption, privileged standing, source replacement, final governance,
continuity completion, or final system identity.

Nothing in this surface becomes sovereignty.
