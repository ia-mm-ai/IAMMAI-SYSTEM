# IAMMAI Derivative Internal Intelligence Pilot Execution Supervision Boundary

## 1. Purpose

This file defines the pilot-execution supervision boundary for derivative internal intelligence participation.

Its job is to answer, in one bounded admissibility note:

- why future pilot execution now requires explicit supervision housing
- what the supervision surface is and is not
- what remains permanently human-held within that surface
- what any future pilot would need to present before execution could even be considered
- what the supervision surface must check, refuse, preserve, and keep closed
- how supervision relates to the existing admissibility stack, branch currentness, checker discipline, and execution trace
- what this note does and does not open

It does not define:

- a constitutional rewrite
- a third-pilot admissibility note
- a third-pilot execution note
- an implementation plan
- a runtime contract
- a vessel rollout
- an agent framework
- a reusable lane design
- an execution scheduler
- an operational dashboard
- a roadmap
- a README
- a project-management note
- a manifesto

This file is additive only. It does not replace repo-scale current-state, readability, rank, or lineage surfaces. It also does not replace existing admissibility, implementation, continuity, runtime, vessel, trace, boundary, or execution case surfaces already standing in the body.

## 2. Why This Note Is Needed Now

Future pilot execution now requires explicit supervision housing because the body has moved past one isolated pilot fact.

The first two pilot cases were supervised in practice. Each used a bounded external proposal flow, human review before repo admission, checker execution against the outside candidate, manual repo admission, and checker execution against the repo copy.

That was sufficient for the first two case-law notes. It is no longer sufficient as an atmospheric pattern if any future execution is ever to be considered.

The pilot-execution trace surface now houses the two executed cases together. Trace housing makes repetition visible. It does not decide who may judge a future case, whether a future case is new evidence, whether the host branch is mature enough, or whether refusal is required.

This pressure comes from actual body growth, not symbolic enthusiasm. The body now needs explicit supervision housing so future execution cannot silently inherit permission from prior success, trace visibility, or checker availability.

## 3. What Already Stands Around This Question

The supervision question comes after the existing boundary stack.

- `admissibility/DERIVATIVE_INTERNAL_INTELLIGENCE_PARTICIPATION_BOUNDARY.md` defines the participation gate and keeps any participant derivative, supervised, non-sovereign, source-limited, and non-self-promoting.
- `admissibility/FIRST_DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_ACTION_BOUNDARY.md` defines one first low-sovereignty pilot action in principle without opening a lane.
- `admissibility/FIRST_DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_ACTION_EXECUTION_CASE.md` records the first executed pilot as one supervised contribution-branch case.
- `admissibility/SECOND_DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_ACTION_ADMISSIBILITY.md` makes one second pilot admissible only as new cross-branch evidence, not as repeat permission.
- `admissibility/SECOND_DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_ACTION_EXECUTION_CASE.md` records the second executed pilot as one supervised decision-branch case.
- `admissibility/DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_EXECUTION_TRACE_BOUNDARY.md` explains why repeated execution needed trace housing before any further case could be considered.
- `admissibility/DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_EXECUTION_TRACE.md` houses the two executed cases together while keeping the body below lane threshold.
- `implementation/CURRENT_IMPLEMENTATION_SURFACES__POST_BRANCH_CONFORMANCE.md` shows implementation-wide branch maturity after decision and contribution-role conformance.
- `implementation/CURRENT_DECISION_RECORD_SURFACES__POST_CONFORMANCE.md` and `implementation/CURRENT_CONTRIBUTION_ROLE_SURFACES.md` show the mature branch-local contexts where the two executed cases occurred.

Supervision housing therefore comes after gate definition, first action narrowing, first execution, second admissibility, second execution, trace-boundary definition, trace housing, and visible branch maturity. It does not precede them and does not replace them.

## 4. What The Supervision Surface Is

The supervision surface is the explicit human-held review surface that would govern whether any future derivative internal intelligence pilot execution may even be considered.

It is bounded by:

- existing admissibility law
- the host branch's current state
- the relevant schema and checker discipline
- the pilot-execution trace
- the no-touch boundaries already stated by the participation and pilot notes

It is non-autonomous. It is not an execution engine, scheduler, dashboard, permission registry, runtime contract, API interface, vessel plan, or authority source.

Its function is to make supervision explicit enough that future pilot work cannot rely on memory, momentum, checker availability, or prior success. It governs consideration. It does not authorize execution by existing.

## 5. What Remains Human-Held

The following remain permanently human-held within this supervision surface.

- branch selection
- pilot activation
- judgment that a proposed case seeks genuinely new bounded evidence
- judgment that the proposed case is not momentum, analogy, or inherited permission
- repo admission approval
- currentness determination
- witness truth
- governance force
- canon or source authority
- family-versus-extension judgment
- expansion from one action into broader permission

No derivative participant may self-select the host branch, self-activate a pilot, decide that prior cases authorize a next case, approve its own repo admission, or promote its own output into authority.

If any of those judgments would need to be delegated to the participant, execution must be refused.

## 6. What Any Future Pilot Would Need To Present

Before any future pilot could even be considered, the proposed case would need to present a bounded supervision packet in substance, not necessarily as a new file.

At minimum, the following would need to be visible.

- the exact host branch
- the host branch's explicit current state or re-entry surface
- the relevant standing schema, if the action touches schema-shaped material
- the relevant bounded checker, if checker discipline is part of the proposed action
- the exact bounded action identity
- the target artifact class and intended artifact path, where applicable
- the exact bounded evidence sought
- the relation to the first and second executed cases already housed in the trace
- the reason the proposed case is not same-branch momentum, analogy by comfort, or permission inherited from prior success
- the expected review, refusal, checker, admission, and re-check sequence
- the specific claims the case would not make even if executed successfully

If these cannot be stated before execution, the proposed case is not ready for supervision review.

## 7. What The Supervision Surface Must Check

The supervision surface must resolve the bounded admissibility questions before any future execution could be considered.

It must check:

- whether the claimed rank is correct
- whether the scope is narrow enough
- whether the host branch is mature enough for derivative touch
- whether the branch current state is explicit enough to prevent drift
- whether the action remains additive, derivative-only, low-sovereignty, and branch-local
- whether the action seeks genuinely new bounded evidence
- whether the action remains below lane threshold
- whether the relevant schema and checker discipline are already standing and adequate for the proposed case
- whether the proposed artifact can remain review-before-admission and checker-visible
- whether the case would pressure runtime, registry, API, vessel, governance, currentness, witness, canon, source, or branch-selection authority
- whether refusal is required instead of execution

These checks are not cosmetic. They are the anti-collapse work of supervision.

## 8. Mandatory Refusal, Pause, Narrowing, And Suspension Boundaries

The supervision surface must refuse execution where any core condition is not met.

Refusal is mandatory where:

- host branch maturity is unclear
- branch currentness is not explicit enough
- the proposed evidence is only repetition, momentum, or convenience
- the action drifts beyond one bounded derivative action
- checker discipline is absent, irrelevant, or being asked to do more than it lawfully does
- repo admission would occur without human approval
- execution would imply runtime, registry, API, vessel, governance, currentness, witness, canon, source, or branch-selection authority
- the proposed case would move the body toward a lane without an explicit lane question
- the participant attempts self-chaining or self-expansion

Pause, narrowing, and suspension are mandatory where blur appears during consideration or execution.

At minimum, the candidate work should stop being treated as active pilot work, the touched branch should return to no-touch posture for that participant, no retry loop should begin, and any later reconsideration should require a fresh explicit admissibility decision.

## 9. What This Note Does Not Yet Open

This note does not open:

- a third pilot
- repeated execution by default
- a reusable lane
- broad branch access
- runtime, API, registry, or vessel operationalization
- autonomous developmental participation

It also does not make supervision itself an execution authorization.

Defined supervision is a precondition for future consideration. It is not permission, activation, execution, lane formation, or operational readiness.

## 10. Relationship To Existing Surfaces

With `admissibility/DERIVATIVE_INTERNAL_INTELLIGENCE_PARTICIPATION_BOUNDARY.md`, this note preserves that supervision is mandatory and that derivative internal intelligence participation remains non-sovereign, source-limited, and non-self-promoting.

With `admissibility/FIRST_DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_ACTION_BOUNDARY.md`, it preserves that even the first low-sovereignty action required explicit human selection, traceability, refusal posture, and no self-expansion.

With `admissibility/FIRST_DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_ACTION_EXECUTION_CASE.md`, it preserves the first supervised execution as case law, not as a supervision system and not as reusable permission.

With `admissibility/SECOND_DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_ACTION_ADMISSIBILITY.md`, it preserves that later execution must justify new bounded evidence rather than inherit permission from success.

With `admissibility/SECOND_DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_ACTION_EXECUTION_CASE.md`, it preserves the second supervised execution as cross-branch case law, not as generalized repeatability.

With `admissibility/DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_EXECUTION_TRACE_BOUNDARY.md`, it preserves that repeated execution required trace housing before further repetition could be considered.

With `admissibility/DERIVATIVE_INTERNAL_INTELLIGENCE_PILOT_EXECUTION_TRACE.md`, it preserves that the trace houses prior cases but does not authorize the next one. Supervision reads the trace; it is not replaced by it.

With `implementation/CURRENT_IMPLEMENTATION_SURFACES__POST_BRANCH_CONFORMANCE.md`, it preserves that future consideration depends on visible implementation branch maturity rather than broad implementation access.

With `implementation/CURRENT_DECISION_RECORD_SURFACES__POST_CONFORMANCE.md` and `implementation/CURRENT_CONTRIBUTION_ROLE_SURFACES.md`, it preserves that branch currentness, schema presence, invalid boundaries, and bounded checkers matter to supervision. These branch surfaces do not themselves grant pilot execution.

This note is therefore supervision housing only. It is not permission and not execution.

## 11. What Remains Open

The following remain open after this note.

- whether any third pilot is ever admissible
- what exact future case, if any, would satisfy supervision
- whether later cases ever cross into lane-question territory
- whether any reusable lane is ever lawful at all
- whether supervision would need stricter recording if future cases were ever separately admitted
- whether any later operational carrier could exist without collapsing supervision into runtime authority

These remain open on purpose. This note defines the supervision boundary; it does not decide the next case.

## 12. Closing Boundary Statement

This file defines the pilot-execution supervision boundary only.

It exists to prevent future pilot execution from remaining half-atmospheric and from silently inheriting permission.

It does not authorize a third pilot, does not create a lane, and does not function as an authority source.
