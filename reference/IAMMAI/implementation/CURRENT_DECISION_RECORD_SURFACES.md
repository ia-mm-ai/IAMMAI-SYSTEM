# IAMMAI Current Decision Record Surfaces

## 1. Purpose

This file defines the current re-entry / current-surfaces note for the decision-record branch.

Its job is to make the decision branch easier to re-enter lawfully by stating, in one compact place:

- what decision surfaces now stand
- what the branch sequence now is
- what the current center of the branch is
- what remains explicitly open

It does not define:

- a constitutional rewrite
- a decision-family master map
- a schema file
- a runtime migration plan
- a storage architecture memo
- a roadmap
- a README
- a project-management note
- a manifesto

This file is additive only. It does not replace repo-scale current-state, readability, rank, or lineage surfaces, and it does not replace the decision surfaces that already stand in the body.

## 2. Why This Note Is Needed Now

The decision branch now has more than one explanatory surface. It now has a visible sequence from implementation-facing overview, through schema-admission and schema-geometry boundaries, into a first-pass schema surface.

That is enough structure that re-entry can now drift in two different ways.

- A later reader can flatten overview, admission, geometry, and schema into one undifferentiated decision layer.
- A later reader can also mistake the existence of a first-pass schema for closure on runtime, registry, storage, currentness, or posture vocabulary questions.

The body therefore now needs one bounded decision-specific current-surfaces note. Its role is not to reopen theory. Its role is to reduce remembering burden and keep the branch sequence readable without widening decision into a larger subsystem.

## 3. What Now Stands In The Decision Branch

The branch spine now stands in the following sequence.

`implementation/DECISION_RECORD_OVERVIEW.md`
: Gives decision explicit implementation-facing objecthood. It distinguishes decision from governance action, state atmosphere, currentness, bridge carry, and generic review prose.

`implementation/DECISION_RECORD_SCHEMA_ADMISSION_BOUNDARY.md`
: Clarifies that decision has crossed from underhoused concern into schema-admissible concern. It does this without claiming runtime admission, final storage placement, or final vocabulary closure.

`implementation/DECISION_RECORD_SCHEMA_GEOMETRY_BOUNDARY.md`
: Clarifies the first-pass geometry answer. Decision should enter schema line through its own explicit envelope, but that envelope should remain state-adjacent, narrow, and non-sovereign rather than opening a broad autonomous decision subsystem.

`implementation/schemas/decision_record.schema.json`
: Makes that bounded geometry real as a first-pass schema surface. It gives decision an explicit conservative envelope with a small required core and optional relation fields, while keeping posture vocabulary and integration pressure intentionally open.

Taken together, these surfaces mean that the decision branch now stands as a real implementation-facing branch with first-pass schema presence. They do not mean that decision runtime integration, registry integration, final canonical rank, or final doctrinal closure are already settled.

The branch spine should be read with the following surrounding grounding surfaces, but not collapsed into them.

These surfaces ground the branch around it. They demonstrate why the branch is lawful and why its distinctions matter. They are not the branch spine itself.

## 5. What The Current Center Of The Branch Is

The current center of the branch is no longer whether decision is real, and it is no longer only whether decision is schema-admissible.

The current center is the first-pass decision schema as the present explicit branch surface, read through the prior overview, admission, and geometry boundaries.

That means the correct current read is:

- decision now has an explicit first-pass schema envelope
- that envelope must still be read as state-adjacent, narrow, and non-sovereign
- the earlier overview and boundary notes remain the lawful reading surfaces for what that schema does and does not mean

Re-entry should therefore follow the branch sequence in order rather than starting from the schema alone or from the surrounding grounding surfaces alone.

These open questions are real. They should remain explicit. The presence of a first-pass schema does not erase them.

## 7. Relationship To Existing Surfaces

This note sits beside existing surfaces as a bounded re-entry aid for decision specifically. It does not become a new authority source.

With the branch spine, it preserves sequence. The overview, admission boundary, geometry boundary, and schema each do different work and should not be flattened into one layer.

With `implementation/CURRENT_IMPLEMENTATION_SURFACES.md`, it narrows one implementation-facing branch without replacing the broader implementation re-entry note.

With `CURRENT_STATE__REPO_ENTRY.md`, `CURRENT_READABILITY_SURFACES.md`, `RANKED_SURFACE_INDEX.md`, and `VERSION_LINEAGE.md`, it preserves that repo-scale current-state, readability, rank, and lineage orientation remain broader than decision alone. This file does not replace those surfaces.

With the grounding surfaces in state-machine, canonical-record, continuity, accession, vessel, and bridge lines, it preserves surrounding architectural support without turning those lines into one undifferentiated decision subsystem.

This note therefore reduces decision-specific re-entry drift. It does not rewrite the branch, replace the branch spine, or convert the branch into runtime doctrine, storage doctrine, or schema migration.

This file defines the current decision-record surfaces only.
