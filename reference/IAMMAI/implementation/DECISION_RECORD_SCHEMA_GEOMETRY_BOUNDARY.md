# IAMMAI Decision Record Schema Geometry Boundary

## 1. Purpose

This file defines the schema-geometry boundary for decision record in first-pass form.

Its job is to answer, in one compact place:

- whether decision should presently enter schema line as a standalone schema envelope or as a bounded extension beside state or standing-state schema work
- what would be lost under extension
- what would be falsely inflated under a too-broad standalone family read
- what the current best bounded geometry answer is
- what that answer would and would not mean

It does not define:

- a constitutional rewrite
- an implementation-family master map
- a schema file
- a runtime migration plan
- a storage architecture blueprint
- a graph or database design
- a roadmap
- a README
- a project-management note
- a manifesto

This file is additive only. It does not replace implementation, runtime, continuity, admissibility, accession, standing, vessel, bridge, review, current-state, or constitutional surfaces already standing in the body.

Later schema work should not proceed from memory, omission, or assumption about whether decision should be hidden inside state or standing-state schema work or given an explicit first-pass envelope of its own.

## 4. Why Geometry Is A Distinct Question

Schema admission is not yet the same as schema geometry.

Schema admission asks whether decision may lawfully become schema at all. Schema geometry asks how that schema should enter the line: as its own bounded envelope or only as an extension within neighboring schema work.

That distinction matters architecturally.

- If geometry is left unresolved, later schema work can drift back into intuition and convenience.
- If decision is hidden inside extension only, the body risks losing the explicit objecthood it just fought to house.
- If decision is treated as a broad standalone family too early, the body risks inflating decision beyond what the visible material actually supports.

This is therefore not cosmetic. It is the boundary between lawful explicit housing and a later return to ambiguity or inflation.

## 5. What Would Be Lost Under Extension

If decision were housed only as a bounded extension beside state or standing-state schema work, the following would likely be lost.

- explicit decision envelope
- clear separation from state atmosphere or a generic posture field
- clear separation from bridge carry
- clear separation from currentness
- recoverability of decision as decision rather than by later interpretation

The visible body already shows why this matters.

`accession/ADMISSION_DECISION.md` is not only a standing-state mood. It is an explicit bounded determination. `vessel/current_state_what_stands_reader_v1/API_BACKED_POSTURE_DECISION__POST_ALIGNMENT_REVIEW.md` is not only a local state note. It is an explicit posture decision. `v1/34_POST_API_BACKED_POSTURE_BRIDGE.md` is not the same thing as the decision it carries.

If geometry were extension-only, the likely result would be that decision again becomes something a skilled reader reconstructs from surrounding state, review, or bridge surfaces rather than something the schema layer preserves explicitly.

## 6. What Would Be Falsely Inflated Under Standalone Family

If decision were treated as a broad standalone family too early, the following would likely be falsely inflated.

- false sovereignty
- false maturity or rank inflation
- premature vocabulary closure
- premature runtime pressure
- subsystem inflation

The visible body does not support decision as a broad autonomous subsystem.

Decision is structurally real, but it still stands nearest state, standing-state, and bounded posture determination. The body does not yet justify a large independent decision architecture with its own broad ontology, runtime lane, or final vocabulary closure.

So “standalone family” would be too large if read as a sovereign subsystem rather than as a narrow explicit envelope.

## 7. Current Best Read Of Schema Geometry

The current best bounded geometry answer is:

**Decision should presently enter schema line through its own explicit first-pass schema envelope, but that envelope should remain state-adjacent, narrow, and non-sovereign rather than opening a broad autonomous decision subsystem.**

This is the strongest truthful answer supported by the visible body.

- It is stronger than mere extension because the body already needs an explicit decision envelope to prevent collapse into state atmosphere, currentness, bridge carry, or generic review prose.
- It is narrower than a broad standalone family because the visible body still grounds decision nearest standing-state structure, scoped determination, and carried consequence rather than a large separate decision world.

So the geometry answer is not “full family” and not “mere extension.”

It is:

- an explicit first-pass decision schema envelope
- placed in the implementation schema line
- read as state-adjacent and standing-state-adjacent
- kept narrow enough that it does not pretend to be a sovereign subsystem

This is geometry clarification only. It is not schema creation.

## 8. What The Chosen Geometry Would Not Mean

The chosen geometry would not mean:

- runtime admission
- checker or mechanism work by default
- final storage or rank decision
- final vocabulary closure
- currentness equivalence
- governance equivalence
- a broad independent decision subsystem

It would also not mean that every posture note automatically becomes a decision record, or that later bridge carry becomes unnecessary once decision has explicit schema geometry.
