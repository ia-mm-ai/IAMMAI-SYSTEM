# IAMMAI Current Implementation Surfaces

## 1. Purpose

This file defines the current re-entry and current-surfaces note for the implementation area.

Its job is to make the implementation area easier to re-enter lawfully by stating, in one compact place:

- what implementation surfaces remain foundational context
- what newer additive implementation-facing surfaces now stand
- what implementation-facing questions remain explicitly open

It does not define:

- a constitutional rewrite
- an implementation-family master map
- a runtime migration plan
- a storage architecture memo
- a schema file
- a graph or database design
- a distributed systems plan
- a roadmap
- a README
- a project-management note
- a manifesto

This file is additive only. It does not replace implementation, runtime, continuity, admissibility, accession, standing, vessel, bridge, review, current-state, or constitutional surfaces already standing in the body.

## 2. Why This Note Is Needed Now

The implementation area now has enough foundational context plus newer additive housing and placement surfaces that re-entry can drift without one bounded implementation-centered note.

The foundational implementation overviews still do the main architectural work. But newer additive surfaces now also stand around contribution role and continuity-object placement. Without one compact note here, a later reader can too easily flatten foundational implementation context, schema-planning context, runtime-preservation context, and newer placement clarifications into one undifferentiated implementation story.

The body therefore needs one small implementation re-entry surface that reduces remembering burden without opening a new family.

## 3. Foundational Implementation Context

The following surfaces remain the foundational implementation context.

`IMPLEMENTATION_MAP.md`
: The orientation surface for the implementation folder. It explains that this area is the first bounded technical derivative set beneath the constitutional and architectural layers.

`SCHEMA_MAP.md`
: The first schema-planning layer. It identifies which schema families should exist first, what they govern, and in what order schema derivation should proceed.

`CANONICAL_RECORDS_OVERVIEW.md`
: The main record-family map. It establishes the distinct canonical families for state, transition, resolution, governance, contribution, witness, validation, and lineage.

`STATE_MACHINE_OVERVIEW.md`
: The implementation-facing state-machine surface. It houses canonical state regimes, lawful transition, orthogonal containment, typed resolution, and lineage-preserving change.

`TRANSITION_RECORD_OVERVIEW.md`
: The transition-specific surface. It keeps lawful movement explicit and reconstructable rather than allowing change to flatten into generic update.

`VALIDATION_ARTIFACT_OVERVIEW.md`
: The validation-specific surface. It keeps bounded condition checking distinct from governance, witness, and semantic source.

`WITNESS_ARTIFACT_OVERVIEW.md`
: The witness-specific surface. It keeps bounded trace of contact distinct from governance, authorship, and semantic source.

`GOVERNANCE_ACTION_OVERVIEW.md`
: The governance-specific surface. It keeps lawful force attributable, legitimacy-bounded, and matter-scoped.

These surfaces remain the implementation area’s main architectural context. They are still the right place to understand the core implementation families and their non-collapse boundaries. They are not the newest additive implementation moves.

## 4. Newer Additive Implementation-Facing Surfaces

The following surfaces now stand as newer additive implementation-facing housing or placement work.

`CONTRIBUTION_ROLE_OVERVIEW.md`
: Gives contribution role its own bounded implementation-facing room. It stops contribution from remaining comparatively underhoused or from collapsing into generic authorship, generic actor language, governance, witness, or validation.

`implementation/CONTINUITY_OBJECT_SCHEMA_PLACEMENT.md`
: Propagates the lineage versus currentness placement distinction into adjacent implementation and schema planning without modifying older implementation files. It keeps lineage and currentness from being read as the same architectural rank.

`continuity/LINEAGE_AND_CURRENTNESS_STORAGE_BOUNDARY.md`
: Provides the storage-rank boundary that implementation needs to read carefully. It clarifies that lineage sits closer to preservable additive continuity relation housing, while currentness remains authority-locating and more derivative.

`continuity/CURRENT_CONTINUITY_SURFACES.md`
: Remains a continuity-side surface, not an implementation file, but it helps implementation re-entry by showing that continuity now has a newer practical housing line rather than only foundational seam-law context.

These surfaces do not replace the foundational implementation context. They narrow ambiguity around record-family underhousing and continuity-object placement.

## 5. What Now Stands In Implementation

Implementation now materially has the following.

- explicit implementation-facing overviews for state, transition, validation, witness, and governance
- a canonical-records surface that already names contribution and lineage as distinct preserved concerns
- a first schema-planning layer that identifies the first schema families while still deferring final infrastructure and storage decisions
- a runtime-preservation contract through `runtime/REGISTRY_CONTRACT.md` that keeps canonical records typed apart and durably preserved
- contribution role now housed in its own bounded implementation-facing overview rather than remaining only a line item inside the canonical-records map
- continuity-object placement now made more explicit for implementation and schema planning through bounded placement clarification rather than ambient continuity prose alone

This is real additive implementation housing.

It is not final implementation closure.
It is not final schema admission.
It is not settled runtime integration.

These surfaces still matter. They should not be flattened into the same layer as the newer additive housing and placement notes.

## 7. What Remains Open

The following implementation-facing questions remain open.

- direct schema-family admission and placement consequences for the newer additive surfaces
- whether and when contribution role receives schema
- whether and how lineage and currentness placement are later absorbed into `SCHEMA_MAP.md`
- runtime and registry integration questions for contribution, lineage, and currentness
- final canonical versus derivative storage implications

These are real open questions. They are not defects in the newer additive notes. They remain open because implementation now needs clearer placement more urgently than it needs final closure.

## 8. Relationship to Existing Surfaces

This note sits beside existing surfaces as a re-entry aid for implementation itself. It does not become a new authority source.

With `runtime/REGISTRY_CONTRACT.md`, it preserves that runtime contract and implementation context are adjacent but not identical. The registry contract governs authoritative preservation. This file helps a reader re-enter the implementation area that must relate to that contract without replacing it.

With `continuity/LINEAGE_AND_CURRENTNESS_STORAGE_BOUNDARY.md` and `implementation/CONTINUITY_OBJECT_SCHEMA_PLACEMENT.md`, it preserves that continuity-object placement has consequences for implementation planning, but those continuity and placement surfaces do not replace the foundational implementation overviews.

With `CURRENT_STATE__REPO_ENTRY.md`, `CURRENT_READABILITY_SURFACES.md`, `RANKED_SURFACE_INDEX.md`, and `VERSION_LINEAGE.md`, it preserves that repo-scale current-state, readability, rank, and lineage orientation remain broader than implementation alone. This file does not replace those repo-entry surfaces.

This note therefore reduces implementation re-entry drift. It does not rewrite rank, runtime, continuity, or the constitutional core.
