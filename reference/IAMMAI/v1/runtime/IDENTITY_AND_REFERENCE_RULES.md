# IAMMAI v1 Identity and Reference Rules

## 1. Purpose

This file defines the bounded v1 cross-cutting identity and reference rules.

Its job is to state, at bounded runtime-law level, how identity and reference are to be understood across canonical artifact bodies, continuity turns, matter relations, explicit execution or envelope relations, and preservation context without silently re-importing the old v0 run-saturated posture through identifier convenience.

It does not define:

- a constitutional rewrite
- a seam declaration
- an authority or inheritance map
- an artifact-boundary decision
- a schema file
- an emitter implementation patch
- a validator code note
- a storage topology design
- a project-management roadmap
- a README

It is a bounded runtime-law document.

## 2. Why This File Is Needed Now

V1 has already re-derived canonical artifact bodies and continuity body.

V1 has already separated body, execution relation, and preservation at contract level. The canonical body schemas for ordinary artifacts and continuity turn already exclude `run_id` from canonical body shape.

Emitter and preservation work now need cross-cutting identity and reference law before implementation hardens convenience into drift. V1 cannot remove `run_id` from canonical bodies while silently keeping run-centric posture alive through id generation, reference naming, or grouped retrieval convenience.

## 3. First Principle

Identity must identify what actually stands.

Reference must point according to lawful relation, not convenience.  
No later carrying or preservation layer may silently redefine earlier identity.

In v1 terms, identity must remain tied to the bounded thing that stands as artifact, continuity turn, matter, execution relation, or preservation context. Reference must preserve the lawful relation between those things rather than flattening them into one generic surface.

## 4. Identity Classes

This runtime law distinguishes the following bounded identity classes:

- canonical artifact identity
- continuity turn identity
- matter identity
- execution identity
- preservation identity

Canonical artifact identity identifies a canonical artifact body as artifact. This includes the ordinary canonical record and artifact families already re-derived in v1.

Continuity turn identity identifies the continuity turn as a canonical continuity-artifact identity. It is a canonical identity, but it is not interchangeable with the ordinary canonical artifact identities merely because all belong to the broader artifact body line.

Matter identity identifies the bounded matter to which a canonical artifact body or continuity turn may lawfully relate.

Execution identity identifies execution occurrence. It identifies bounded runtime occurrence, not canonical artifact standing.

Preservation identity identifies where and how a preserved object or preserved relation was preserved or carried in preservation context.

These identities are related but non-equivalent. Exact final string syntax remains open here. V1 identity law requires distinction, not premature formatting closure.

## 5. Reference Classes

This runtime law distinguishes the following bounded reference classes:

- canonical artifact reference
- matter reference
- predecessor continuity reference
- explicit execution-relation reference
- preservation or context reference where relevant

Canonical artifact reference points from one lawful surface to another canonical artifact where that artifact-to-artifact relation is part of what the body preserves.

Matter reference points to bounded matter relation where matter scope is part of artifact or continuity standing.

Predecessor continuity reference points from one continuity turn to a prior continuity turn where lawful append-oriented succession is part of continuity standing.

Explicit execution-relation reference points to execution occurrence only where execution relation must remain explicit and lawfully preserved.

Preservation or context reference points to preservation placement or preservation-bearing context where such reference is needed for retrieval or reconstructability without changing canonical identity.

No reference class may silently stand in for another by convenience.

## 6. Anchor and Predecessor Law

Canonical artifact anchoring and predecessor succession are not the same relation.

Canonical artifact anchoring keeps continuity subordinate to preserved canonical reality by linking continuity to the preserved canonical artifacts that actually anchor it.

Predecessor succession may support append-oriented continuity by making lawful succession explicit across continuity turns.

Predecessor succession must not silently replace canonical artifact anchoring. Continuity therefore remains subordinate to preserved canonical reality rather than generic sequence, generic memory, or atmospheric continuity display.

## 7. Execution Relation Law

Execution relation may be preserved explicitly where lawful.

Execution relation is not canonical artifact identity. It is not default continuity identity. It identifies execution occurrence and any lawfully preserved relation to that occurrence.

Execution relation must remain explicit rather than ambient. It must not be smuggled back into canonical artifact identity or canonical continuity identity through naming convenience, implicit prefixing, or default reference assumptions.

## 8. Preservation Relation Law

Preservation may preserve identity-bearing objects and their lawful relations.

Preservation placement does not create or redefine canonical identity. It preserves what already stood and what was lawfully related before preservation.

Retrieval convenience must not rewrite identity or reference class. A preservation handle is not automatically a canonical artifact identity, a continuity identity, a matter identity, or an execution identity merely because it helps retrieve preserved material.

## 9. Current-v0 / Desired-v1 Distinction

Current root identity and reference posture remains historically real v0 lineage.

V0 identity and reference behavior was strongly run-centric. The root line often let run occurrence shape emitted ids, canonical-looking references, and preservation reading.

V1 identity and reference law must therefore be stated explicitly rather than silently inherited from that convenience path. This is not blame language. It is the explicit statement that v1 cannot move into implementation while leaving its identity and reference posture governed by v0 drift under cleaner names.

## 10. Anti-Collapse Rules

A conforming v1 posture must not allow:

- run-centric identifier convenience standing in for canonical artifact identity
- predecessor-only reading that severs continuity from canonical artifact anchoring
- preservation handle pretending to be artifact identity
- execution handle pretending to be canonical reference
- grouped retrieval surface erasing reference-class distinctions

It must also not allow continuity and ordinary artifacts to be read as one undifferentiated reference surface simply because both participate in later preserved relation.

## 11. Downstream Consequences

Later emitter re-derivation must follow these identity and reference rules.

Later preservation implementation must follow these rules. Later fixture generation and retrieval must remain readable through these rules.

This file is the cross-cutting bridge before concrete implementation work. It requires later implementation surfaces to preserve identity class and reference class distinctions rather than quietly re-importing v0 collapse patterns through convenience naming, grouping, or retrieval posture.

## 12. Closing Boundary Statement

This file defines bounded v1 identity and reference rules only.

Later files or implementation work may realize these rules in emitter and preservation surfaces. This file exists so v1 can move into implementation without re-importing v0 collapse patterns through identity and reference convenience.
